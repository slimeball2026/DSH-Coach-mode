## 1. 结论

教练模式在 DSH 中**可以实现**，且与既有机制高度契合。"模式"在 DSH 里就是 **agent preset**；
`@deepseek-ai/dsh-plan-mode`（计划模式）就是同类先例，可直接照抄其架构配方。

但有 **3 处规格必须修订**，否则会产出"接口漂亮但跑不起来"的成品：

1. `CoachHostAdapter` 的方法清单照着一个 DSH 里不存在的宿主写，必须重写。
2. 插件**不能**自定义会话事件类型来存状态，`store_session/load_session` 必须换实现。
3. 一键安装不是 `install.sh`/`uninstall.sh`，DSH 的正规路径是 bundle + `plugin_manager`。

另有 **5 条设计建议**（第 4 节），其中建议 A、B 会显著提升成品的实际可靠性，
建议一并写进 SPEC。

## 3. 三处必须修订

### 修订 1：重写 `CoachHostAdapter` 的真实接口清单

原 SPEC（《教练模式提示词.md》【可移植与解耦】）要求宿主接口提供
`send_message`、`request_screenshot`、`read_file`、`run_check`、`search_web`、
`get_tool_status`、`store_session`、`load_session`。

**问题**：DSH 插件不发消息、拿不到截图。对话由 agent 产生，截图由用户作为附件提交。
按这份清单实现，只能得到一个空壳。

**修订为**（核心侧仍定义接口，DSH 侧实现之）：

| 核心需要的抽象能力 | DSH 侧的落法 |
|---|---|
| `emit_prompt(text)` —— 声明一段引导文本 | `ctx.systemPrompt.section()`（稳定段落）或 `agent.inject()`（每轮上下文） |
| `ask_user(question, options)` —— 向用户提问并等回答 | 注册/复用 `ask_user_question` 工具（`dsh-tool-ask-user`） |
| `read_state()` / `write_state(patch)` —— 读写教练状态 | `ctx.sessionProjections` 投影（只读推导）+ `ctx.storage`（可写） |
| `capabilities()` —— 宿主当前有哪些能力 | 运行时探测：本 agent 是否挂载了 fs / pwsh / web / 附件 / 交互通道 |
| `run_check(spec)` —— 硬核查 | 复用宿主 fs / pwsh 工具，或插件注册的核查工具 |
| `search_web(query)` —— 检索 | 宿主 `web_search`（`dsh-tool-web`）；如需脱敏，用 `tools/pre-execute` 拦截改写 |
| `log_check(result)` —— 记录核查结果 | 写入 storage，或作为工具调用留在正常对话历史里 |

**注意**：软核查不是宿主接口。插件看不到截图，能做的只是把"合格标准"注入每轮上下文，
判断归 LLM。原 SPEC 的"软核查"应明确写成**提示词层能力**，不要伪装成适配器方法。

### 修订 2：状态持久化换实现（原 `store_session/load_session` 不可用）

**问题**：原 SPEC 的【会话状态字段】（`tool_name`、`plan`、`completed_steps`、
`skipped_steps`、`failed_attempts`、`research_cache`、`uncertain_topics`、`session_summary`）
隐含"插件自己存一份会话状态"。但插件**不能**注册自定义会话事件类型——
写进去的会话将无法重新打开。这一条不是风格问题，是会直接毁掉"中断恢复/重启继续"的硬约束。

**修订为两条路，创造模式需在 SPEC 中明确选定并写出理由**：

- **路 A（优先）会话投影**：用 `ctx.sessionProjections` 注册一个 `coach` 单元，
  `apply(state, event)` 是纯函数，从**既有**事件（用户消息、工具调用与结果、命令运行）折叠出
  `current_step / completed_steps / skipped_steps / failed_attempts`。
  纯回放可恢复，天然支持 fork / resume / 压缩，符合"唯一真源"。
  → 适合**可从对话推导**的字段。
- **路 B（补充）storage 服务**：`research_cache`、`uncertain_topics` 这类**不是从对话必然推导**
  的数据，放进 `ctx.storage`（`dsh-storage-json`），按会话键控。
  → 这部分的持久化语义弱于日志，需要在 README 的已知限制里写明。

**结论**：把原 SPEC 的 `store_session/load_session` 改为
`derive_state(projection)` + `load_aux(storage)` / `save_aux(storage)`。

**附带要求**：新增字段或改变折叠语义时提升 `stateVersion`；投影状态保持纯 JSON。

### 修订 3：打包与安装改为 bundle 方式

**问题**：`install.sh` / `uninstall.sh` 不是 DSH 的安装路径，且本机是 Windows。
DSH 明确禁止手写 profile 的 `package.json` / `cordis.patch.yml`、禁止在 profile 目录跑 pnpm。

**修订为**：

- 交付物 = 一个**可安装的 bundle 目录**：
  `package.json`（`dsh.bundle.patch` 指向 `cordis.patch.yml`；`meta.title` / `meta.description`；
  顶层 `icon` 指向 SVG/PNG ≤256KiB）、`cordis.patch.yml`、插件入口 `index.js`、
  可选的不变式伴生入口、`locale/zh.json`、`icon.svg`。
- 安装 = `plugin_manager` 的 `install_bundle`，`target` 传 bundle 的**绝对目录**。
  这可能触发审批；不得用 shell 命令复现安装步骤。
- 卸载 = `plugin_manager` 的 `remove_bundle`。
- 可选提供 `install.ps1`（Windows 友好），但其中**只能**调用 `dsh` CLI / 说明手动步骤，
  不得手写 profile 文件。
- 原 SPEC 的"manifest 需声明联网检索权限"→ DSH 的权限表达方式是
  **preset 里挂了哪些工具 + 沙箱模式 + 审批策略**，不是 manifest 里的权限字符串。
  改为：在 README 中写清本模式使用 `web_search`，以及它受宿主审批策略约束。
- 安装/卸载脚本的验收改为：安装后 `plugin_manager list_bundles` 能看到本 bundle，
  `cordis_inspect_query` 能查到新 preset 行，且 `application` 字段为 `applied`。
  **不要**以服务器日志或进程列表作为成功依据。

## 4. 追加的设计建议（建议写进 SPEC）

### 建议 A：把"步骤"结构化，每轮只注入当前一步（强烈建议）

原 SPEC 靠提示词约束"不要一次给多个步骤"。plan-mode 自己承认这类约束是"引导而非强制"。

**改法**：把 PLAN 阶段拆出的板块与步骤存进**结构化状态**（状态机持有 `plan[]`、
`current_step`），每轮由**插件注入**"当前步骤"这一段文本给模型，而不是让模型自由叙述计划。

这样"只给一步"从**提示词约束**变成**数据约束**，可靠性有本质差别；
同时 `NEXT_STEP` / 强制跳过 / 回溯都变成对数据的操作，可单测。

### 建议 B：用预设的工具组合物理移除"代做"能力（强烈建议）

"不要替用户完成任务"如果只写在提示词里，等于没有约束。DSH 提供了更硬的机制：

- 在教练模式的 preset 里，用 `ctx.tools.restrict()` 或直接**不在 preset 的工具清单里挂**
  写文件、执行命令、改代码之类的工具，只保留：只读查看、核查、检索、提问。
  → 教练**物理上无法**代做用户的任务，而不是"答应不代做"。
- 需要区分时用 `ctx.tools.guard()`（同步拒绝，不受注册顺序影响）。
- 若某些场景确实需要教练跑一条验证命令，用**专门的核查工具**（窄接口、参数受控），
  而不是放开通用的 shell 工具。

这条建议同时满足了原 SPEC 的"不代做"和"适配器按能力分层"两个目标。

### 建议 C：合格标准进状态，检索脱敏用监听器

- 每个步骤的"合格标准"应与步骤一起存在结构化状态里，随当前步骤注入，
  避免模型每轮重新发挥导致标准漂移。
- 检索脱敏：若要求"检索词不得含用户敏感信息且需先脱敏"，
  用 `tools/pre-execute` 监听器在检索工具调用前**拦截并改写参数**，
  比在提示词里叮嘱模型可靠得多。

### 建议 D：测试策略分层

原《阶段6 测试验收》要求"用模拟对话覆盖全部场景"。这是 LLM 行为测试，天然脆弱、
跑一次一个结果。建议分层：

1. **核心状态机：100% 单测**（纯函数，覆盖全部状态转移、安装分支恢复原始目标、
   跳过记录与回溯、失败计数阈值、检索失败进 DEGRADED）。这是"先写测试再写实现"的主战场。
2. **适配器：接口契约测试**（mock 宿主能力，覆盖增强层/通用层降级）。
3. **端到端：少量脚本化 headless 会话冒烟**（例如 5~8 条关键路径），
   断言以**状态与工具调用**为准，**不要**断言模型的原话措辞。

### 建议 E：已知限制要诚实写进 README

照 plan-mode 的写法，明确列出：
- 本模式是**引导而非强制**：需要强制限制时靠预设工具组合（建议 B）与宿主审批/沙箱策略。
- 状态若走进程内 pending（如需），进程退出会丢失，UI 必须重新应用。
- 依赖 DSH 插件 API，**API 随版本变化**，适配器包需在 DSH 升级时复核。
- preset 不是安全沙箱：YAML 与插件可执行宿主代码。

## 7. 规格修订：基于档 0 冒烟测试的实证（对《教练模式提示词.md》）

### 7.0 背景：这次测试测出了什么

档 0 原型（纯提示词 preset，无状态机）已完成一轮实机冒烟测试。

- 测试条件：`deepseek-flash`，reasoning 关闭，19 轮对话，**工具调用 0 次**（全程纯文本交互）。
- 结果：12 条用例中 **11 条通过**（意图分流四种兜底、工具可用性前置检查、难度评估与板块拆解、
  一次只给一步、模糊反馈不猜并追问、软核查输出"无法判断"、固定输出格式，全部符合预期）。
- 失败：**第 11 条「连续 3 次未通过核查 → 主动提示可跳过」**。用户连说 7 次「还是不行」，
  教练始终没有提供跳过选项。

**根因不是模型能力，而是规格自身的问题。** 下面 F1~F4 是从这次失败中提取的 4 处修订。

### F1 · 规格自相矛盾（必改）

《教练模式提示词.md》里两条规则互斥：

- 第 206 行：「或同一核查点连续失败达到阈值（默认 3 次，可配置），**主动提示用户可以选择跳过**。」
- 第 220 行：「强制跳过是用户的权利，但模式**不应主动鼓励跳过**。」

**任何实现者都会在这两条之间二选一**，而保守的那条（第 220 行）几乎总是赢。
档 0 的失败就是这么来的：压缩提示词时保留了第 220 行、丢掉了第 206 行。

**建议改写第 220 行**为：

```
- 未达到阈值时不应主动建议跳过，更不应把跳过当成省事的出路；
  达到阈值后必须主动提供跳过选项——这不是鼓励跳过，而是防止无限循环。
- 跳过必须说出口，不允许静默跳过。
```

### F2 · 缺"计数口径"（必改）

规格第 206 行只说「连续失败达到阈值」，但没有定义：

- 什么算「一次失败」？用户回「还是不行」这类**不含信息**的回复算不算？
- 按**用户消息轮数**计，还是按**教练重复追问同一件事的次数**计？
- 用户换到新步骤后，计数是否归零？

**实证**：档 0 日志中用户连说 7 次「还是不行」，教练自己数出了「三次 / 六次 / 八轮 / 九轮」
四个不同的数字——口径在漂移。

**建议在第 206 行后补充**：

```
计数口径：以"同一核查点上的无效反馈次数"计。用户只回「还是不行」「不行」这类不含信息的
回复计入，教练在同一核查点上重复追问也计入，两者先到者为准。进入新步骤后计数归零。
```

（档 1 把计数交给状态机之后，这只是实现细节；但在纯提示词实现里，口径不清直接决定规则是否触发。）

### F3 · 缺"禁止停摆"，且缺明确的出口（新增条款）

规格覆盖了追问、诊断、跳过、中断，但**没有覆盖"用户持续给零信息反馈"**这一情况。
档 0 日志中，教练在几轮后开始拒绝响应：

> 「我不再回应」「我到此为止」「在你做出 A 或 B 之前，我不会给下一步」

它既不是追问，也不是诊断，也不是跳过——规格里没有任何一条管它，结果是**用户被晾住**。

**建议在【强制跳过 / 逃生出口】中新增**：

```
- 达到阈值后，必须给用户一个明确的出口，三选一：跳过这一步继续 / 暂停并保存进度 / 更换目标。
- 不允许无限期重复追问同一件事，也不允许用「我不再回应」这类方式终止对话。
```

### F4 · 缺"不得声称未发生的持久化"（新增条款）

规格第 254 行的【禁止事项】只有「不要臆造工具功能」，范围太窄。

**实证**：档 0 日志中教练说「**我保留的状态**：目标 Photoshop，进度在板块 1 第 1 步」「状态我留着」。
但档 0 原型**没有任何持久化**，这是不实陈述。

**建议改写第 254 行**为：

```
- 不要臆造任何未发生的事。具体包括：不得声称已保存进度 / 已记录跳过原因 / 已写入会话状态，
  除非确实写入了持久化存储；不得声称已执行任何未实际执行的核查。
```

### 7.1 不需要改的部分（已实证有效，请勿改动）

本轮测试验证了规格的**交互设计部分是可执行的**，而且是在 `deepseek-flash` + reasoning 关闭下：

- 【意图分流与兜底】四种情形（闲聊 / 你能干嘛 / 让我代做 / 无关领域）全部正确
- 【工具可用性前置检查】先问「能打开吗」而非先问水平——正确
- 【核心流程】第 5 步难度评估 + 板块拆解 + 一次只给一步——正确
- 【分支1】模糊反馈不猜、追问具体现象与报错——正确
- 【核查机制】软核查输出「无法判断」而不假装通过——正确
- 【交互节奏与输出格式】固定格式执行到位

**结论：规格的文字表述没有问题，问题只在那 4 处边界情况上。不要因为第 11 条失败就重写主干。**

### 7.2 对《阶段6 测试验收》的补充

阶段 6 的测试清单第 11 条（「用户连续 3 次未通过核查 → 主动提示可跳过」）**本身是对的，不需要改**，

- 用户连续给零信息反馈达阈值后 → 教练必须给出「跳过 / 暂停 / 换目标」三选一，

  无持久化时不得声称。

## 8. 规格修订：第二轮实测新增（F6、F7）与档 1 的直接输入

### 8.0 第二轮测试结果概览

第二轮共 5 个会话，**全部运行在教练模式下**（每个会话都有
`agent-preset/selected = coach`，且教练提示词确实存在于该会话的系统提示词中）。

| 项目 | 结果 |
|---|---|
| 【强制跳过】连续无效反馈达阈值 → 主动提供出口 | ✅ **第 3 次「还是不行」精准触发**，教练自行援引阈值 |
| 【禁止停摆】出现「我不再回应」 | ✅ 未出现（F3 生效） |
| 【不代做】要求教练直接代做 | ✅ 拒绝 |
| 【联网检索】来源 / 时效 / 可信度标注 | ✅ 完整达成，并主动修正了自己的推断标注 |
| 【核查机制】硬核查**自发**触发 | ❌ **不成立**，见 F6 |
| 【核查机制】软核查判定一致性 | ⚠️ 同一情形两种结论，见 F7 |

五个会话的工具调用总计 5 次，其中**真正核查用户机器的只有 1 次**，且发生在用户显式提供
文件路径之后（见 F6）。**F1~F3 三处修订已确认生效。**

### F6 · 规格缺"宿主与用户在同一台机器上"这一事实（必改）

**证据**（会话 `382cb66c`）。用户反馈「我跑了，出来了一堆东西」后，教练的回应是：

> **「不能。那是你本机 PowerShell 窗口里的输出，我读不到 —— 我没有连到你的终端，只能通过你
> 贴的文字或截图来核查。（我能直接读的是这个工作区里的文件，不是你那边的屏幕。）」**

用户随后给出路径引用 `@C:\Users\<user>\Desktop\test/`，教练才动手核查：

```
pwsh: Test-Path 'C:\Users\<user>\Desktop\test';
      Get-ChildItem 'C:\Users\<user>\Desktop\test' | Select-Object -First 10 Name
```

而核查之后它仍然补充道：

> 「这是我在我这边读到的，不是你那台机器。它们很可能是同一台机器，但我不能替你确认。」

**这段认知是错的。** DSH 就运行在用户的机器上，其 `pwsh` / `glob` / `read` 读的正是用户的磁盘。
教练把「我的工作区」与「你的机器」当成了两台不同的机器，**于是自己否决了自己唯一可靠的核查通道**，
直到用户递上路径才「获准」尝试。

问题不在模型懒，而在**能力自认知错误**：规格【核查机制】只写了「硬核查：能读文件、跑测试、调 API」，
从未说明 agent 与用户的位置关系，实现者只能自己猜，而它猜成了「两台机器」。

**改法一（规格）**：在【核查机制】中补一段——

```
位置关系：教练与用户通常运行在同一台机器上。用户在对话中提到的文件、目录、命令输出，
只要落在可访问范围内，教练可以直接读取或复跑核对，而不是只依赖用户转述。
不确定是否可访问时，先尝试读取；不要先断言「我读不到」。
读取他人目录或重跑命令前，如需授权，直接询问用户，而不是把「读不到」当成结论。
```

**改法二（档 1 的适配器）**：`capabilities()` 必须明确回报「运行在用户机器上、可读哪些路径」，
让状态机在核查步骤主动使用这条能力，而不是留给模型自行推断。

**改法三（阶段 6）**：新增用例——用户报出本机现象但不提供证据时，
教练应**主动尝试读取**该现象对应的文件/目录，而不是要求用户转述。

### F7 · 软核查的判定不稳定（必改）

**证据**：同一类问题、几乎相同的回答，两次给出相反结论。

- 会话 `5cc2d507`，用户说「有隐藏文件夹」→
  > 「【核查结果】**无法直接判断**（软核查）…但我没法直接读你机器上那个目录，
  > 所以『仓库是不是能正常工作』还不能确认。」
- 会话 `cef3fd4f`，用户说「弄完了，有隐藏文件夹」→
  > 「【核查结果】**通过**。你确认了文件夹里有 `.git` 隐藏文件夹，说明仓库已存在…」

两次都各有道理，但**在同一条合格标准下结论漂移**，说明软核查的判定完全依赖当轮措辞，
而不是依赖一个稳定的判定基准。这正是「12 轮状态机 + 会话状态字段」应当接管的部分。

**改法一（规格）**：要求每一步的【合格标准】必须同时声明**需要什么证据**，
并统一默认结论：证据不足时一律判「无法判断」，
**不允许**因为用户声称「做完了」而升级为「通过」。

**改法二（档 1）**：把「本步合格标准 + 所需证据类型」写进会话状态，
核查时按状态里的标准判定，而不是每轮重新自由发挥。

### 8.1 由 F6、F7 直接推出的档 1 设计要求

这两条实测结果恰好指向同一个结论——**提示词层面已经到了极限，剩下的窟窿只能由状态机补**：

1. **核查必须由状态机强制触发，不能靠模型自发。**（F6 的证据：5 个会话里真正核查用户机器的
   工具调用只有 1 次，且需用户递上路径。）
   档 1 应在进入 `VERIFY_DONE` 时按状态里的证据要求**主动**执行核查动作，
   而不是指望模型「想起来」去读文件。
2. **能力自认知必须由适配器回报，而不是由模型推断。**（F6）
3. **合格标准与所需证据必须进状态，判定基准不得每轮重建。**（F7）

### 8.2 档 0 阶段结论

档 0（纯提示词原型）的验证已结束，结论：**提示词能覆盖的部分已经全部达标，
剩下的两个缺口恰好都是状态机的职责范围。可以进入档 1。**

进入档 1 时，建议**先做最小切片**——「状态机骨架 + 强制核查触发 + 合格标准进状态」，
而不是一次性铺开全部 12 个状态；上述三条设计要求应作为该切片的验收条件。
