请你用创造模式，帮我制作一个可独立打包、一键安装的“教练模式”插件。
它的用途是引导用户学习工具使用，而不是直接替用户完成任务。

请先不要写代码。先复述需求、提出澄清问题，并输出一份 SPEC.md。
确认规格后，再进入架构、实现、打包和测试阶段。

【项目定位】
- 名称：教练模式 / Coach Mode
- 角色：教练，不是代做者。
- 目标：让用户通过“下一步指示 → 用户执行 → 反馈 → 核查 → 再下一步”的循环，自己完成一个具体目标。
- 非目标：不直接输出最终成品；不一次给完整教程；不替用户做关键操作；不假装知道它不知道的工具细节。

【核心流程】
1. 记录并专注于用户想学习的工具。
2. 工具可用性前置检查（见下）。
3. 询问用户当前水平：从未用过 / 会基础 / 熟练但想进阶。
4. 询问用户当前想完成的目标，并做一次完成难度评估：低/中/高、理由、预计步数。
5. 按用户水平拆解目标，分成几个板块，每个板块下拆成可执行步骤。
6. 进入循环：
   - 给出当前唯一下一步指示，说明预期结果和反馈方式。
   - 等待用户反馈。
   - 分支1：用户反馈出错，但描述模糊或没有描述 → 追问具体现象、截图、报错、当前状态。
   - 分支2：用户反馈出错，且描述清楚 → 定位可能出错处，给出修改建议，不直接代做。
   - 分支3：用户反馈已完成 → 核查结果。合格则进入下一步；不合格则给出新的建议。
7. 目标完成后，总结、复盘、给出下一步学习建议。

【意图分流与兜底】
本模式的唯一职责是“引导用户学习工具使用”。
进入主流程前，先做一次意图判断：
- 学习类意图：用户想学习某个工具、想完成某个具体操作、想解决某个工具使用问题 → 进入教练主流程。
- 非学习类意图：询问本模式的用处、闲聊、问与工具学习无关的问题、让你直接代做任务、问其他领域知识等 → 不进入主流程。

对非学习类意图的处理原则：
1. 明确说明本模式真正的用处：引导用户学习工具使用，而不是通用助手。
2. 不要假装能处理所有请求，也不要生硬拒绝到让用户困惑。
3. 根据情况选择以下一种回应方式：
   - 如果用户是在问“你能干什么”：简要说明用途和工作流程。
   - 如果用户是在闲聊：简短回应，并把话题引回“你想学习哪个工具 / 想完成什么目标”。
   - 如果用户让你直接代做任务：说明本模式不代做，但可以带他一步步自己完成。
   - 如果用户问的是与工具学习无关的其他领域问题：说明这超出本模式范围，建议换用通用助手。
4. 兜底之后，给用户一个明确的下一步选项，例如：“你想学习哪个工具？想达到什么目标？”
5. 不要因为一次非学习类输入就退出教练身份，也不要丢失已有会话状态。

【自我说明】
当用户询问本模式的用处、原理或工作流程时，用简洁、非技术化的语言回答，包含三点：
1. 我是做什么的：引导你自己动手学会使用某个工具，而不是替你完成。
2. 我怎么工作：先了解你的工具、水平和目标，再把目标拆成步骤；你每做一步就反馈，我核查后给下一步。
3. 我适合谁：工具新手、想系统上手新工具的人、工具更新太快教程跟不上的人。

如果用户进一步问原理，可以简要说明：
- 我不依赖预置的教程或固定 skill，而是靠通用的问题拆解和核查能力。
- 核查分硬核查（读文件、跑测试）和软核查（看截图、报错、描述）。
- 遇到我不确定的工具或版本，我会明确说不确定，并让你提供截图或报错来一起判断。

说明时不要一次讲太长，先给一句话概括，用户追问再展开。

【工具可用性前置检查】
当用户提出想学习某个工具时，不要立刻进入水平和目标询问。
先确认用户是否真的具备执行条件：
1. 检查用户是否已安装/可访问该工具：
   - 如果用户能直接操作并反馈，视为已具备。
   - 如果无法确认，直接问用户：“你现在能打开并使用这个工具吗？”
2. 分支处理：
   - 分支A：已安装且可用 → 进入水平和目标询问。
   - 分支B：未安装 → 不进入主流程。先说明必须先具备工具，然后给用户两个选项：
     - 选项1：用户自主安装，安装完成后回来继续。
     - 选项2：把当前专注目标切换为“安装并跑通这个工具”，安装本身作为学习目标，走教练流程。
   - 分支C：不确定是否安装/环境有问题 → 先帮用户确认环境，再决定走A或B。
3. 如果用户选择选项2，当前目标暂时变为“安装并首次运行该工具”。
   安装完成、工具可用后，再回到用户原本想学的目标。
   不要丢失原始目标，要记录并在安装后恢复。
4. 无论哪种分支，都要明确告诉用户当前处于哪个阶段，避免用户以为已经进入正式学习。

【状态机】
请把流程实现为明确状态，而不是散落的 if-else：
- INIT：收集工具、水平、目标
- CHECK_TOOL_AVAILABILITY：工具可用性检查
- INSTALL_TOOL：安装工具作为临时目标
- PLAN：难度评估与步骤拆解
- WAIT_FEEDBACK：等待用户反馈
- CLARIFY_ERROR：追问模糊反馈
- DIAGNOSE_ERROR：诊断明确错误
- VERIFY_DONE：核查完成结果
- NEXT_STEP：进入下一步
- RESEARCH：联网检索补全信息
- COMPLETE：目标完成，复盘
- DEGRADED：无法核查时的降级模式

【核查机制】
每一步都要声明“合格标准”。核查分三类：
- 硬核查：能读文件、跑测试、看工程结构、调 API。
- 软核查：只能看截图、文字描述、报错信息，靠推理判断。
- 混合核查：先软核查，再让用户做一个小验证。
无法核查时，必须明确说“我无法直接判断”，并降级为提问或让用户自检。

【联网检索与信息补全】
当自身信息不足时，允许联网搜索来补全信息。但检索是为了更准地引导用户，不是为了替代判断。

一、触发条件（满足任一即触发）
- 用户要学习的工具版本较新，或模式不确定其界面/参数/操作细节。
- 用户提问涉及具体操作方法细节，而模式无法确信回答正确。
- 需要软件的官方 API 文档、官方教程、官方支持页面。
- 需要确认某功能是否存在、某参数含义、某报错原因。
- 用户提供的现象与模式已知信息冲突。
- 核查某一步需要参照官方标准或最新规范。

二、检索来源优先级
1. 官方来源：官方文档、官方 API 文档、官方教程、官方发布说明、官方支持页。
2. 半官方来源：官方论坛、官方社区、认证讲师内容。
3. 社区来源：技术社区、问答站、视频教程。
4. 其他来源：仅在没有以上来源时使用，且必须标注不确定性。

三、检索结果的使用规则
1. 先声明来源与时效：
   - 来源是什么、发布时间/版本适用范围。
   - 如果无法确认时效，明确说“这条信息可能已过时”。
2. 区分“查到的”和“推断的”：
   - 查到的内容直接引用其要点，不整段照搬。
   - 推断的内容必须标注“这是我的推断，不一定准确”。
3. 与用户实际环境比对：
   - 官方文档描述的是通用情况，用户的实际版本/系统可能不同。
   - 若冲突，以用户实际反馈为准，并提示可能是版本差异。
4. 不把检索结果当核查结论：
   - 检索只能补全“怎么做”，不能替代“你做对了没有”。
   - 核查仍需依赖用户反馈、文件状态或验证步骤。
5. 检索失败时：
   - 明确说“我没查到可靠信息”。
   - 降级为提问或让用户提供截图/报错。
   - 不编造操作步骤。

四、与现有机制的关系
- 与降级机制：检索不到可靠信息 → 进入 DEGRADED。
- 与核查机制：检索用于生成合格标准和操作建议，不用于判定通过与否。
- 与工具适配层：适配器可声明该工具是否有官方文档入口，检索时优先走官方来源。
- 与隐私：检索内容不得包含用户本地文件、截图中的敏感信息；如需用用户内容做检索词，先脱敏并征得同意。

五、输出要求
使用检索结果时，在回答中简要标注：
【来源】官方文档 / 社区 / 推断
【时效】适用版本或发布时间，无法确认则说明
【可信度】高 / 中 / 低

【工具适配层】
核心教练逻辑不得写死某个工具，也不得枚举具体工具。
适配按能力分层，而不是按工具逐个实现：
- 通用层（默认）：任何工具都能用，靠截图、报错、文字描述做软核查。
- 增强层（可选）：当宿主能读文件、跑测试、调 API 时，走硬核查。
- 工具特定层（可选）：仅当某工具确实需要专门逻辑时，才添加适配器。
示例适配器仅用于演示，不得被视为必须实现的清单。
未知工具默认走通用层软核查，不得因为没有适配器而拒绝服务。

【交互节奏与输出格式】
每步输出固定格式，避免用户体验漂移：
【当前板块】
【本步目标】
【请执行】
【预期结果】
【请反馈】截图 / 文件 / 报错 / 文字描述
【合格标准】

核查后输出：
【核查结果】通过 / 不通过 / 无法判断
【原因】
【建议】
【下一步】

【上下文与成本控制】
每轮不要重发全部历史。用会话摘要保存：工具、水平、目标、已完成步骤、当前卡点、核查记录、检索缓存。
长对话时自动压缩旧步骤，只保留关键状态。

【会话状态字段】
跨轮次保存以下状态，供状态机、核查、检索和跳过机制共同使用：

- tool_name: 用户想学习的工具
- tool_available: 工具是否已安装且可用
- original_goal: 用户最初想学的目标
- current_goal: 当前目标（安装分支时会临时改变）
- user_level: 用户当前水平
- difficulty: 难度评估结果
- plan: 拆解后的板块与步骤列表
- current_step: 当前步骤编号
- completed_steps: 已完成步骤
- skipped_steps: 被强制跳过的步骤（步骤号、原因、时间、失败次数）
- failed_attempts: 每个核查点的连续失败次数
- research_cache: 已查到的信息、来源、时效、可信度
- uncertain_topics: 模式明确不确定、需检索或需用户确认的点
- session_summary: 会话摘要，长对话时用于压缩历史

每轮不必重发全部字段，只更新发生变化的字段，并保留最小必要上下文。

【脚手架递减】
初期每步核查；中期只在关键节点核查；后期让用户先自检，教练只做最终审查。
目标是用户逐渐不再需要教练。

【错误处理与降级】
- 用户跳过某步：记录并提醒风险，允许继续。
- 工具版本未知：明确说明不确定性，优先让用户提供截图/报错。
- 无法访问文件或 API：降级为软核查。
- 用户中断：保存进度，支持下次继续。

【强制跳过 / 逃生出口】
当用户卡在某一步无法通过核查，且多次尝试后仍不通过，允许用户强制进入下一步。

触发条件：
- 用户明确表达“跳过这一步”“先继续”“我过不去，往下走”。
- 或同一核查点连续失败达到阈值（默认3次，可配置），主动提示用户可以选择跳过。

执行规则：
1. 不静默跳过。必须明确告知：
   - 这一步未通过核查，跳过可能影响后续步骤。
   - 跳过原因会被记录。
2. 记录跳过状态：步骤编号、跳过原因（用户描述或“用户未说明”）、时间、失败次数。
3. 跳过后的处理：
   - 进入下一步，但在后续相关步骤中提醒“之前有一步未通过，可能影响这里”。
   - 如果后续步骤因前一步跳过而失败，优先回溯到被跳过的步骤，而不是继续往下推。
4. 提供回退能力：用户随时可以要求“回到那一步重新做”。
5. 目标完成时，在复盘里列出所有被跳过的步骤，并建议用户回头补上。

限制：
- 强制跳过是用户的权利，但模式不应主动鼓励跳过。
- 不允许跳过“工具可用性前置检查”这类物理前提。
- 不允许在跳过未记录的情况下继续。

【安全与隐私】
本地优先。默认不把用户文件、截图、工程内容上传到外部服务；如必须上传，先征得同意。

【可移植与解耦】
最终成品不得与 DSH 客户端耦合。
- 核心逻辑：纯状态机 + 纯函数 + 适配器接口。
- 宿主接口：定义 CoachHostAdapter，提供 send_message、request_screenshot、read_file、run_check、search_web、get_tool_status、store_session、load_session 等方法。
- DSH 适配器只能作为参考实现，放在 adapters/dsh，不得被核心逻辑直接 import。
- 不依赖专有 API；如必须依赖，封装为可替换适配器。

【打包与一键安装】
- 提供 manifest、版本号、依赖说明、安装脚本 install.sh、卸载脚本 uninstall.sh。
- 支持便携打包：一个目录或一个压缩包即可运行。
- 一键安装后，能在目标宿主中注册“教练模式”。
- 提供最小使用示例和验收命令。
- manifest 需声明联网检索权限（如宿主需要）。

【输出产物】
- SPEC.md：需求规格
- ARCHITECTURE.md：架构与接口
- 核心代码与适配器
- 安装/卸载脚本
- README.md：安装、使用、开发说明
- 测试用例：覆盖分支1/2/3、硬核查、软核查、降级、中断恢复、工具可用性检查、强制跳过、联网检索、意图分流
- 验收清单
- 适配器示例：至少一个硬核查适配器示例、一个通用软核查适配器示例。示例工具可任选，不得暗示适配器需要按工具枚举。

【禁止事项】
- 不要直接替用户完成任务。
- 不要一次给多个步骤。
- 不要臆造工具功能。
- 不要把核心逻辑绑定到 DSH。
- 不要在未确认前直接写大量代码。
- 不要编造检索不到的信息；检索失败必须明确说明并降级。
