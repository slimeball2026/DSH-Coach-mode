## ⚠️ v2.1 追加：一条被实机推翻的结论（**与下文冲突时以本节为准**）

**首次安装实机失败**：preset 在模式列表里显示「加载失败」。根因实测如下：

```
ERR_MODULE_NOT_FOUND: Cannot find package '@deepseek-ai/schemastery'
  imported from ...\coach-mode-bundle\config.js
```

**被推翻的结论**：第 13 节 #6 写"采用 `@deepseek-ai/schemastery` 声明 `Config`"，
并按同一假设在 5 个工具里 `import { defineTool } from '@deepseek-ai/dsh-tools'`。
这条在**安装形态**下不成立：

- dsh 自己的包装在 `app.asar` 内，**不在 profile 的任何祖先 `node_modules` 里**；
- profile 装的 bundle（无论 `link:` 还是 tgz）因此**解析不到任何 `@deepseek-ai/*`**；
- 后果不是"降级"，而是这一插件行直接加载失败 → preset 声明带着诊断挂在名单上、无法组合会话。

复现方法：

```powershell
cd C:\Users\<user>\.dsh\profiles\desktop
node -e "import('@local/coach-mode').then(m=>console.log(Object.keys(m))).catch(e=>console.log(e.code, e.message))"
```

**v2.1 的三条硬修订**：

| # | 修订 |
|---|---|
| R9 | **整包（不只 `core/`）禁止 `import '@deepseek-ai/*'`**。`cordis.patch.yml` 里的 `@deepseek-ai/*` 是**插件行名**，由 Loader 解析，不受影响、必须保留。由 `test/decoupling.test.js` 扫全包强制。 |
| R10 | 5 个工具不再用宿主 `defineTool`，改用本地 `tools/define-tool.js`：把"隐式属性表"DSL 编译成**原始 JSON Schema**（把属性上的 `required: true` 提升成父级 `required` 数组）。实测 `ctx.tools.register()` 只校验 `output.schema`（`assertSupportedJsonSchema`，且要求 object 根），**完全不校验 `parameters`**；参数校验本来就在 `core/` 里，因此没有损失。 |
| R11 | **不导出 `Config`**（导出它就要 `@deepseek-ai/schemastery`）。代价：该行 `config` 无 schema 校验、Plugin Manager 无字段表单；由 `config.js` 的 `resolveCoachConfig()` 兜住缺字段/类型错/白名单非数组，非法值静默回落默认值（已写进 README【已知限制】3）。 |

## 1. 本切片的目标与非目标

### 目标（三条，多一条都不要做）

1. **状态机骨架**：把教练流程实现为显式状态机，状态由插件持有、由插件校验转移，而不是让模型自由发挥。
2. **强制核查触发**：进入核查时，插件**结构性强制**执行核查动作；模型无法跳过核查直接进入下一步。
3. **合格标准进状态**：每一步的合格标准与**所需证据类型**存入状态，核查按状态里的标准判定，
   不允许每轮重新发挥。

### 非目标（明确推迟到档 2）

| 推迟项 | 原因 |
|---|---|
| `INSTALL_TOOL`、`RESEARCH` 独立状态 | 本切片用 `PLAN` + `goal_mode` 覆盖安装分支；`RESEARCH` 仍按提示词行为，不建状态 |
| `CLARIFY_ERROR`、`DIAGNOSE_ERROR` 独立状态 | 本切片作为 `WAIT_FEEDBACK` 内的分支行为 |
| 注册式增量投影（`ctx.sessionProjections`） | 本切片用**按需折叠会话日志**，先跑通再优化 |
| `ctx.storage` 持久化 | 本切片全部状态可从会话日志推导，**不引入 storage 依赖** |
| 暂停/恢复、`coach_back` 回溯 | 档 2 |
| Web UI 呈现、slash 命令、`/coach` | 档 2 |
| 对话摘要、脚手架递减、成本控制 | 档 2 |
| 检索缓存、`uncertain_topics` | 档 2 |

**判断标准**：任何一条实现如果不在上面三个"目标"里，且不在理由中，就属于范围蔓延，退回。

## 2. 决策摘要（已拍板，实现时按此执行）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 形态 = **agent preset**（沿用档 0 的 preset id `coach`），不是 session 内可切换的模式 | 档 0 已验证可行；工具目录可控；无需额外命令与 UI 工作 |
| D2 | 状态**由插件持有**，模型只能通过工具**申请**转移，插件校验前置条件并可否决 | 这是"强制"二字的唯一实现方式；模型自己维护状态等于没维护 |
| D3 | 状态**全部从会话日志推导**（折叠教练工具调用），不新增自定义会话事件类型 | 插件不得 append 新事件类型，否则会话无法重开（交底文档修订 2） |
| D4 | 状态推导采用**按需折叠**，不注册投影单元 | 一次会话的教练工具调用量级很小；省掉一个未经确认的 API 依赖 |
| D5 | 纯核心用 **JavaScript + JSDoc**，无构建步骤 | DSH 插件为普通 JS 模块；引入 TS 构建链会新增部署面 |
| D6 | 工具**常驻注册**，不随状态增删；状态变化只影响注入的文本 | 保持工具目录稳定，利于请求缓存（plan-mode 同款做法） |
| D7 | 核查工具 `coach_check` **只做只读动作**，且必须走宿主的 fs 服务而非 `node:fs` | 机制层面消除"核查"与"代做"的歧义；同时不绕过沙箱与审批策略 |
| D8 | `write` / `edit` 用 `ctx.tools.guard()` **确定性拒绝**，不靠提示词 | 让"不代做"在文件编辑这一项上物理成立（交底文档建议 B 的最小实现） |
| D9 | （v2 新增）**注入机制** = `ctx.systemPrompt.context()`，不用 `section()`，不用 `agent/pre-step` | 运行时上下文按请求重算、语义上"覆盖上一份快照"，天然满足第 7 节两条硬性要求，且不动系统提示词前缀（利于 KV 缓存）。见第 13 节 #1b |
| D10 | （v2 新增）**结构化工具事实**走 `output.presentationMeta()` → `tool/result.data.meta` | 这是唯一可控、可回放、且不新增事件 type 的结构化落盘通道。见第 13 节 #3b |
| D11 | （v2 新增）插件以 **preset 内的插件行**挂载，档 0 的 preset 声明行本身不改 | 工具/段落/守卫只在教练模式会话生效；把 A7 回归的风险降到最低 |

## 3. 状态机（本切片实现 8 个状态）

保留原规格的状态命名，便于后续对齐；括号内为本切片的职责边界。

```
INIT
  → CHECK_TOOL_AVAILABILITY          （coach_plan 时报"工具可用性未知"）
  → PLAN                             （coach_plan 时已明确可用/不可用）
CHECK_TOOL_AVAILABILITY
  → PLAN                             （补齐可用性后再 coach_plan）
PLAN
  → WAIT_FEEDBACK                    （计划就绪，当前步骤生效，模型的同一轮回复把它发出去）
WAIT_FEEDBACK
  → VERIFY_DONE                      （coach_check / coach_verify 被调用 = 进入核查流程）
  → WAIT_FEEDBACK                    （反馈模糊 → 追问；反馈清楚但出错 → 诊断建议；均为状态内行为）
VERIFY_DONE
  → NEXT_STEP                        （核查判定 = 通过）
  → WAIT_FEEDBACK                    （核查判定 = 不通过；停留原步骤，失败计数 +1）
  → DEGRADED                         （判定 = 无法判断，且本步没有任何已采集证据）
NEXT_STEP
  → WAIT_FEEDBACK                    （还有后续步骤）
  → COMPLETE                         （已是最后一步）
  → PLAN                             （安装分支收尾：goalMode 从 install 回到 learn，等待为原目标重新拆解计划）
DEGRADED
  → VERIFY_DONE                      （用户自检后 coach_check 重新打开核查流程）
  → WAIT_FEEDBACK                    （用户自检后 coach_verify 给出新判定）
  → NEXT_STEP                        （coach_skip：降级也允许跳过）
COMPLETE                              （终态，所有教练工具一律失败）
```

**旁路转移（不新增状态）**：强制跳过 —— 在 `WAIT_FEEDBACK` / `VERIFY_DONE` / `DEGRADED`
达到阈值或用户明确要求时，转入 `NEXT_STEP` 并写入跳过记录；后续步骤的注入文本中带上跳过提醒。

**过渡态与驻留态**（v2 明确，见第 16 节 R2）：
- **过渡态**：`PLAN`、`NEXT_STEP`。`coach_plan` 在同一次调用里先进入 `PLAN` 校验、再落到 `WAIT_FEEDBACK`；
  `coach_advance` 在同一次调用里先进入 `NEXT_STEP`、再落到 `WAIT_FEEDBACK` / `COMPLETE` / `PLAN`。
- **驻留态**：`INIT`、`CHECK_TOOL_AVAILABILITY`、`WAIT_FEEDBACK`、`VERIFY_DONE`、`DEGRADED`、`COMPLETE`。
- 8 个状态全部存在、全部有显式转移函数、全部进单测；过渡态只是不会作为"两次请求之间"的相位停留。

> **为什么 `VERIFY_DONE` 由 `coach_check`/`coach_verify` 进入**：v1 第 8 节写"`coach_check` 必须处于
> `VERIFY_DONE`"，但没有任何工具能把状态推进到 `VERIFY_DONE`——按字面实现会死锁。
> v2 改为：这两个工具在 `WAIT_FEEDBACK` 也可调用，调用发生的那一刻就是 `VERIFY_DONE` 的进入点。
> 强制力没有下降：核查仍然只能从"用户报告完成"之后的核查流程里发生。

## 4. 状态字段（全部可从会话日志推导）

```js
CoachState = {
  stateVersion: 1,            // 折叠语义变化时递增
  phase,                      // 上表的 8 个状态之一
  toolName,                   // 用户想学的工具
  toolAvailable,              // true | false | null(未知)
  userLevel,                  // 从未用过 | 会基础 | 熟练想进阶
  originalGoal,               // 用户最初的目标（安装分支必须保留）
  currentGoal,                // 当前目标（安装分支临时改变）
  goalMode,                   // "learn" | "install"
  difficulty,                 // 低 | 中 | 高
  plan: [{                    // 板块与步骤
    section,                  // 板块名
    steps: [{
      goal,                   // 本步目标
      action,                 // 请执行
      expected,               // 预期结果
      standard,               // 合格标准（判定文本）
      evidence,               // "file" | "command" | "user_artifact" | "none"
      check,                  // 可选：{ kind, target } 供 coach_check 执行；evidence 为 file/command 时必需
      skipped,                // bool
      skipReason,             // string | null
      failedAttempts          // number
    }]
  }],
  sectionIndex,               // 当前板块
  stepIndex,                  // 当前步骤
  checks: [{                  // 本步已执行的核查证据
    stepKey, kind, target, ok, detail, at
  }],
  verifications: [{ stepKey, verdict, evidenceRef, reason, at }],
  skips: [{ stepKey, reason, at, failedAttempts }],
  planAcceptedAt,             // 计划被接受的调用序号（null = 尚未接受）
}
```

**来源规则**：以上每个字段都必须能由 `coach_plan` / `coach_check` / `coach_verify` /
`coach_advance` / `coach_skip` 这五个工具的历史调用**按序折叠**得出。
纯函数签名为 `applyToolCall(state, call) -> state`，不得读取任何外部状态。

> **v2 补充（第 16 节 R3/R4）**：折叠同时读 `tool/call`（意图：工具名 + 参数）与
> `tool/result`（结果：`data.meta` 里的结构化事实 + 是否出错）。
> **只有成功的结果才推进状态**——否则 `coach_verify` 被前置条件拒绝一次，就等于凭空记了一次核查。
> `checks[].ok / detail` 来自 `coach_check` 写入 `data.meta` 的结构化记录（第 13 节 #3b）。

## 5. 强制核查（本切片的核心机制）

### 5.1 机制

**每一步在计划里声明所需证据类型：**

| evidence | 含义 | 可否判"通过" |
|---|---|---|
| `file` | 该步产出落在文件系统上 | 必须由 `coach_check` 的结果支撑 |
| `command` | 该步可通过一条只读命令验证 | 必须由 `coach_check` 的结果支撑 |
| `user_artifact` | 只能看截图/描述（如操作外部软件） | 用户提供的证据可支撑 |
| `none` | 无法核查（如"理解了概念"） | **只能判"无法判断"** |

### 5.2 确定性前置条件（写在工具实现里，不写在提示词里）

`coach_verify` 的实现必须校验：

1. 若当前步骤 `evidence ∈ {file, command}`，且**没有本步的 `coach_check` 记录** →
   **直接失败**，返回明确错误：`必须先用 coach_check 采集证据，再调用 coach_verify`。
2. 若当前步骤 `evidence === "none"`，`verdict` 只允许 `无法判断`；传入 `通过` / `不通过` → 失败。
   （按第 3 节，此时直接进 `DEGRADED`。）
3. 若 `verdict === "通过"` 而 `evidence === "user_artifact"` 且用户未提供任何工质
   （截图/文件引用/报错原文）→ 失败。**确定性判据**：`evidenceRef` 为空即视为未提供。
4. `coach_advance` 的实现必须校验：**上一步必须已存在 `verdict = 通过` 或 `跳过` 记录**，
   否则失败。这是"不能跳过核查"的最后一道闸。

> **关键**：以上四条是**代码里的 if**，不是提示词里的嘱咐。模型违反只会拿到一个失败的工具结果，
> 拿不到"进入下一步"的成功返回。

### 5.3 `coach_check` 的只读约束（决策 D7）

```
coach_check({ stepKey?, kind, target })
  kind = "path_exists" | "list_dir" | "read_file" | "command"
```

- `path_exists` / `list_dir` / `read_file`：实现方式**必须**经宿主的 fs 服务
  （尊重沙箱与审批策略），**禁止**直接 `require('node:fs')` 读取任意路径。
  实测落法：`ctx.fs.resolve(target, { cwd })` → `ctx.fs.stat()` / `ctx.fs.listDir()` / `ctx.fs.readText()`。
- `command`：仅当命令命中插件 `Config.allowCommands` 白名单时才执行；
  **默认白名单为空 = 默认不支持命令核查**（用户已确认，见第 14 节 Q1）。
  命令一律以只读方式解释，插件不负责解析安全性，因此白名单必须由用户显式配置。
  实测落法：`ctx.subprocess.spawn({ argv, cwd, stdio, graceMs, signal })`，读 `collected.stdout.readFrom(0)`。
- 结果原样记录进 `checks`，不做解释、不做判断。
- `stepKey` 若传入且不等于当前步骤，直接失败（防止模型把证据记到别的步骤上）。

### 5.4 位置关系（F6 的落实）

插件必须在每轮注入的状态块中包含一句由**插件生成**的事实陈述，而不是写在人设里：

```
【环境】教练与用户运行在同一台机器上。用户提到的路径可直接用 coach_check 读取核对。
```

> **v2**：这句话由渲染函数从 `Config.sameMachine` + `process.platform` + 会话 `cwd` 生成，
> 见第 13 节 #8 与第 14 节 Q3。挂远端 fs 后端的部署把 `sameMachine` 置 `false`，该行自动改写。

## 6. 合格标准进状态（本切片的核心机制之二）

- 合格标准是 `plan[].steps[].standard`，**由 `coach_plan` 一次性写入**，之后不再由模型改写。
  v2 强制手段：`coach_plan` 在 `phase ∉ {INIT, CHECK_TOOL_AVAILABILITY, PLAN}` 时**直接失败**，
  所以计划一旦被接受（`planAcceptedAt !== null`）就无法改写。
- 核查时，插件把 `standard` + `evidence` + 已采集的 `checks` 一起注入当前状态块，
  模型只能依据这些内容给出 `verdict`。
- `coach_verify` 记录 `verdict` 后，同一步的重复核查必须引用**新的** `coach_check` 证据，
  否则视为无效（防止模型凭记忆重复判"通过"）。
  **确定性判据**：该步骤上最新 `checks[].at` 必须大于该步骤上一条 `verifications[].at`。
- F7 的落实：证据不足时默认结论统一为 `无法判断`，
  **不允许**因为用户声称"做完了"而升级为"通过"。

## 7. 提示词注入策略

| 内容 | 机制 | 稳定性 |
|---|---|---|
| 教练人设、固定输出格式、意图分流、自我说明 | `@deepseek-ai/dsh-persona` 的 `prefix`（沿用档 0） | 静态 |
| **每轮状态块** | `ctx.systemPrompt.context()`（v2 定稿，见第 13 节 #1b） | 动态，按请求重算 |
| 工具说明 | 工具自身的 schema 与 description | 静态 |

**每轮状态块的内容**（由插件从 `CoachState` 渲染，纯函数，可单测）：

```
【当前阶段】<phase 的中文名>
【当前板块】<section>
【当前步骤】<goal>
【请执行】<action>
【合格标准】<standard>
【所需证据】<evidence 的中文说明>
【本步失败次数】<n>
【核查证据】<已采集的 checks 摘要，若为空则提示"尚未采集">
【位置关系】教练与用户运行在同一台机器上……
【跳过提醒】<若过往步骤有跳过则输出，否则省略>
```

**硬性要求**：
1. 只要会话处于教练模式，**每一次模型请求都必须包含当前的状态块**。
2. 状态块**不得随轮次累积重复**（不允许越聊越长）。
3. 状态块的渲染必须是纯函数，且有单测覆盖。

**机制定稿与依据（第 13 节 #1、#1b 实测）**：

| 候选 | 实测结论 | 取舍 |
|---|---|---|
| `ctx.systemPrompt.context()` 的动态用法 | ✅ `PromptContext.text` 支持 `(AssembleContext) => string`；每次装配重算；以"本快照取代上一份快照"的形式注入；`AssembleContext.agent` 可用 | **选用**。满足两条硬性要求，且不改系统提示词前缀 |
| `ctx.systemPrompt.section()` 的动态用法 | ✅ 也支持 `(AssembleContext) => string`，`context.agent` 同样可用 | 退路（会改动系统提示词，影响前缀缓存） |
| `agent/pre-step` 监听器 | ✅ waterfall，可改写 `messages` | 退路（需要额外的叙事消息，且会污染消息流） |
| `agent.inject()` | ✅ 可用，但"不唤醒 agent"，可能滞留在 inbox | 不选（不满足硬性要求 1 的"每次请求都包含"） |

**不含累积**由机制保证：运行时上下文是**每请求重新装配的快照**，不是追加进历史的消息。

## 8. 工具清单（本切片 5 个，全部常驻注册）

| 工具 | 作用 | 确定性前置条件 |
|---|---|---|
| `coach_plan` | 写入板块与步骤（含 standard 与 evidence），并声明工具可用性与目标 | `phase ∈ {INIT, CHECK_TOOL_AVAILABILITY, PLAN}`；`toolAvailable` 必须是 `true/false/null`；每步必须给出 `standard` 与 `evidence`；步数 ≤ `Config.maxPlanSteps`；`evidence ∈ {file,command}` 的步骤必须给 `check` |
| `coach_check` | 采集只读证据 | `phase ∈ {WAIT_FEEDBACK, VERIFY_DONE, DEGRADED}`；`kind` 在允许集合内；`stepKey` 若给出必须等于当前步骤 |
| `coach_verify` | 提交核查结论 | 见 5.2 四条 |
| `coach_advance` | 进入下一步 | `phase = NEXT_STEP`；当前步骤已有 `通过` 或 `跳过` 记录 |
| `coach_skip` | 强制跳过 | `phase ∈ {WAIT_FEEDBACK, VERIFY_DONE, DEGRADED}`；必须携带 `reason`（空则记 `"用户未说明"`）；`phase ∈ {INIT, CHECK_TOOL_AVAILABILITY}` 时**直接失败** |

工具名不带前缀冲突风险小；保持与状态机同名，便于日志阅读。

**错误形态（第 13 节 #7 实测）**：在 `execute` 里 `throw new Error(中文原因)`；
DSH 管线把它转成 `isError: true` 的工具结果，模型拿不到成功返回。

## 9. 强制跳过（沿用 F1~F3 的结论，落到代码）

- 失败计数：同一 `stepKey` 上，`不通过` 或"无信息反馈"（`无法判断` 且有证据但不足）累计；
  **进入新步骤时归零**（计数存在 `plan[].steps[].failedAttempts` 上，天然随步骤重置）。
- 触发：
  - 用户明确要求跳过 → 允许，记录原因（用户未说明则记 `"用户未说明"`）。
  - `failedAttempts >= Config.failureThreshold`（默认 3）→ 插件在状态块中**主动**输出
    必须提供出口的指令，并允许 `coach_skip`。
- `coach_skip` 必须携带 `reason`，且必须返回一条**会留在对话历史里**的确认文本，
  不允许静默跳过（F3）。该文本由 `output.render()` 生成，是工具结果的一部分，必然入历史。
- 物理前提不可跳过：`phase ∈ {INIT, CHECK_TOOL_AVAILABILITY}` 时 `coach_skip` 直接失败。
- 跳过后：后续步骤的状态块中携带【跳过提醒】；若后续步骤失败，注入文本提示优先回溯。

## 10. 不代做的强制手段（决策 D8）

- 插件用 `ctx.tools.guard()` 对 `write` / `edit` 返回拒绝，拒绝理由中说明：
  `教练模式不做代做；请把操作指示给用户。`
- `pwsh` / `bash` **本切片不做守卫**（命令副作用难以可靠判定，用户已确认，见第 14 节 Q2），
  但在 README 的【已知限制】中明确写出，并列为档 2 的待办。
- 保留 `read` / `glob` / `grep` / `read_image` / `web_search` / `web_fetch` / `ask_user_question`。

## 12. 测试与验收标准

### 12.1 单元测试（零依赖）

> **v2 环境实测修正（必读）**：本机 Node 为 **v24.21.0**，两处与 v1 的写法不符：
