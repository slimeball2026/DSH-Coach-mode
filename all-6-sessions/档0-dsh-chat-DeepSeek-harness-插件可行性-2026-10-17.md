##### 三、必须改的三处（这是我最想让你在交给创造模式之前定掉的）

**1. `CoachHostAdapter` 的方法清单是照着一个不存在的宿主写的。**
`send_message`（聊天由 agent 自己发，插件不发消息）、`request_screenshot`（截图来自用户附件，插件拿不到）、`get_tool_status`/`load_session` 这些名字在 DSH 里没有对应物。真实的 seam 只有这几个：**提示词段落、`agent.inject()` 注入上下文、工具注册（含 `ask_user_question`）、会话投影 `sessionProjections`、`ctx.storage`、web search 服务、fs/shell 工具是否存在**。这份接口不改，创造模式就只能发明一套假接口，最后交付物是个跑不起来的空壳。

**2. 插件不能自定义会话事件类型——`store_session/load_session` 这条要重写。**
DSH 的插件开发规范里明确写着：**会话日志是唯一真源**，而实时 `Session.append()` 无法设置 `ignorable` 标记，所以插件自己 append 一个新 `type` 的事件会导致**该会话之后无法重新打开**。plan-mode 能用 `plan/mode` 事件是因为它是一方包。所以教练状态的持久化只能走两条路之一：从既有会话事件做**投影（projection）**推导，或放进 **storage 服务**（`dsh-storage-json`）。这个改动直接决定"中断恢复""重启继续"能不能成立，必须在 SPEC 阶段定死。

**3. 一键安装不是 `install.sh` / `uninstall.sh`。**
DSH 的正规安装路径是**bundle 目录 + `plugin_manager install_bundle`**（会走审批），而且明确禁止手写 profile 的 `package.json` / `cordis.patch.yml`、禁止在 profile 目录跑 pnpm。何况你在 Windows 上，`.sh` 脚本本来也跑不了。建议：交付 bundle + 可选 `install.ps1`，安装说明写清 `plugin_manager` 的用法；卸载用 `remove_bundle`。

**另外一条设计建议（会显著提升可靠性）：** 你担心的"不要一次给多个步骤"，纯提示词确实管不住。但把"拆解出的板块与步骤"做成**结构化状态**，每轮只把**当前一步**注入模型上下文，"只给一步"就从**提示词约束**变成了**数据约束**——这是 plan-mode/教练模式这类包唯一可靠的强制手段。同理，"不替用户做"最硬的手段不是嘱咐模型，而是在这个 preset 里用工具组合**物理移除**写文件、执行命令之类的工具，只留只读、核查、检索、提问。这两点建议写进 SPEC，成品质量会完全不一样。
