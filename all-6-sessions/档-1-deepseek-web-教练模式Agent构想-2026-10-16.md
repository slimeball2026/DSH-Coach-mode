# 问题 1: 我想到一个可能有趣的Agent的模式，我...

我想到一个可能有趣的Agent的模式，我管它叫"教练模式"，它不负责帮用户处理工作，而是一步步给出下一步的指示，当用户处理过后让Agent进行核查就给出结果并进入下一步。工作内容不仅包括代码，还包括一下专业工具例如传统的ps pr，还有更多新兴的工具等等，太新的可能不在参数和skill里面。
也许它很适合作为新手学习工具的好方式

# 💡 回答 1

你这个“教练模式”的想法很有意思，而且切中了一个当前 Agent 设计里被低估的方向。

## 为什么这个模式有价值

现在主流 Agent 的思路是“代劳”——你给目标，它出结果。但很多场景下，用户真正需要的不是结果，而是**学会自己产出结果的能力**。这两者的差别很大：

*   **代劳模式**：用户得到鱼，但下次遇到类似问题还是不会。
*   **教练模式**：用户自己动手，Agent 只负责“下一步做什么、做完对不对、为什么错”。

尤其在你提到的 PS、PR、新兴工具这类场景里，很多知识是**隐性的、步骤性的、依赖上下文的**，很难靠一篇教程覆盖。教练模式本质上是把“师傅带徒弟”的过程产品化了。

## 这个模式的关键设计点

**1. 核查是核心难点，也是护城河**

给下一步指示不难，难的是“用户做完后，Agent 怎么判断对不对”。不同工具的核查方式完全不同：

*   代码：跑测试、看 diff、静态分析，相对容易。
*   PS/PR：可以看工程文件结构、图层、时间线、导出参数，但“做得好不好”很难自动判断。
*   新兴工具：可能连 API 都没有，只能靠用户截图/描述，Agent 做“软核查”。

所以教练模式可能天然要分两类：**可硬核查的**（有文件/API/测试）和**只能软核查的**（靠用户反馈）。后者更像苏格拉底式对话，而不是自动化流水线。

**2. “太新的工具不在参数和 skill 里”这点很关键**

这恰恰是教练模式相对传统教程/课程的优势所在。传统教程是静态的，工具一更新就过时；而教练模式可以：

*   让用户把当前界面截图/报错贴进来，Agent 现场推理下一步。
*   把用户的实际操作反馈当作“最新文档”来用。
*   不依赖预置 skill，而是依赖**通用的问题拆解 + 核查能力**。

这其实是在用 Agent 的泛化能力，去补预置知识的滞后性。

**3. 节奏控制是体验成败的关键**

教练模式最容易犯的错是：一次给太多步，变成变相教程；或者每步太碎，用户觉得被当小孩。好的节奏应该是：

*   一次只给一个可执行、可验证的动作。
*   明确告诉用户“做完后给我看什么”（截图/文件/报错）。
*   核查后不只说对错，还要说“为什么”，以及“如果错了通常是哪几种原因”。

## 可能的产品形态

我脑子里浮现出几种：

*   **IDE/工具内嵌**：在 PS 里装个面板，逐步引导并读取当前文档状态核查。
*   **对话式教练**：用户开着工具，Agent 在旁边的聊天窗口里一步步带。
*   **任务闯关式**：把学习目标拆成关卡，每关一个核查点，适合新手系统学习。

## 一个需要想清楚的问题

教练模式的**终止条件** 是什么？是用户完成某个具体任务，还是用户达到“不再需要教练”的水平？前者好定义，后者才是“学习工具”的真正目标，但很难衡量。可能需要在过程中逐步**撤掉脚手架**——比如从“每步都核查”过渡到“只在关键节点核查”，最后变成“你自己做，我只看结果”。

总的来说，我觉得这个方向很有潜力，尤其适合**工具类技能 + 新手 + 工具更新快** 这三个条件叠加的场景。你是想把它做成一个通用框架，还是先针对某个具体工具（比如 PS 或某个新工具）做原型？

# 问题 2: deepseek harness的创造模...

deepseek harness的创造模式也许很适合做这个，评估一下这个项目可能需要多少token？

# 💡 回答 2

用 DeepSeek Harness 的创造模式来做你这个“教练模式”，确实是个很自然的契合点——创造模式的核心就是“Agent 检查自身运行时、在内存中试验插件、组合新的运行模式” [凤凰网科技](https://tech.ifeng.com/c/8vZ0azYi0Sf) [dsh-lark-bot — Tools plugin for DeepSeek Harness | dshbase](https://dshbase.com/zh/blog/deepseek-harness-modes/)，这正好对应“核查用户操作 + 动态生成下一步指示”的循环。

但你的问题“需要多少 token”不好直接给一个精确数字，因为教练模式的 token 消耗结构很特殊。我帮你拆一下：

### 单次“教练循环”的 token 量级

假设一次交互是：用户贴状态（截图/文件片段/报错）→ Agent 核查 → 给出下一步指示。

**输入侧** 大概几百到几千 token，取决于你贴什么。文字描述很省，截图要看 harness 是否走多模态通道。

**输出侧** 取决于“指示 + 解释”的长度。教练模式的优势是输出通常比“代劳模式”短——你不需要让 Agent 生成完整代码或文件内容，只需要给一个动作指令 + 简要核查结论。几百到一两千 token 比较合理。

**但真正的消耗不在单次，而在上下文累积**。教练模式是长对话，每一轮都要把之前的交互历史带上。如果你做 50 步，第 50 轮时输入可能已经累积到几万 token。

### 成本参考（按 DeepSeek 当前价格）

deepseek-flash 缓存未命中输入空闲时段 1元/百万 token，输出 4元/百万 token [DeepSeek](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/?gspk=aXZvanVuaW9yOTk2&gsxid=oDJY7ORpjqboON&ps_partner_key=aXZvanVuaW9yOTk2&ps_xid=oDJY7ORpjqboON&pscd=get.youai.ai&utm_campaign=general&utm_content=ivojunior996&utm_medium=referral&utm_source=partnerstack)。一次教练循环假设输入 2k + 输出 1k，成本约 0.006 元。做 100 轮也就几毛钱。**模型成本本身不是瓶颈。**

### 真正要担心的不是 token 费用，是“啰嗦税”

有第三方评测数据显示 DeepSeek V4.1 Flash 是同期“最啰嗦”的模型之一，完成一个任务平均烧 8.9 万 token，比上一代多出 62% [Tencent](https://cloud.tencent.com.cn/developer/article/2745213?from=15425&frompage=seopage#3)。教练模式恰恰需要 Agent **克制输出**——它只说“下一步做什么、为什么、做完给我看什么”，不该展开长篇解释。如果模型习惯性啰嗦，token 消耗会远高于理论值。

### 创造模式做教练的独特消耗点

创造模式比标准模式多一层开销：Agent 要读取和推理自身运行时配置、可能临时挂载插件来“造一把扳手” [dsh-lark-bot — Tools plugin for DeepSeek Harness | dshbase](https://dshbase.com/zh/blog/deepseek-harness-modes/)。但你不需要每次都做这种事。更实际的路径是：**用创造模式先“造出”一个教练预设，之后用那个预设跑教练循环**。造预设的一次性 token 成本高，但后续每次教练交互就回到正常量级了。

另外要注意，创造模式的信任边界等同 shell 访问，它会在 live runtime 上执行模型生成的 JavaScript [GitHub](https://github.com/hezi2020/dsh-plugin-wiki/blob/main/wiki/docs/usage/runtime-modes.md#1)。教练场景下用户给的信息（截图、报错）可能包含非受信内容，这个安全边界需要你设计时多想一步。

### 给你的建议

先别算精确 token，先跑一个 **10 步的小原型**，用创造模式现场造一个极简教练预设，记录每轮实际 token 消耗。你会得到比任何估算都准的数据。

# 问题 3: deepseek harness的创造模...

deepseek harness的创造模式也许很适合做这个，评估一下，要做出教练模式这个项目可能需要多少token？

# 💡 回答 3

结论先行：**无法给出精确的 Token 估算，但可以给出一个合理的量级判断和结构拆解。** 如果只是做一个“教练模式”的演示原型，成本可能在 **百万级 token 以内**；如果要达到可用的学习工具水准，持续开发消耗会显著更高。

### 为什么“创造模式”适合做这个

DeepSeek Harness 的创造模式（cordis）允许 Agent 检查自身运行时、在内存中试验插件、组合新的运行模式 [凤凰网科技](https://tech.ifeng.com/c/8vZ0azYi0Sf) [dsh-lark-bot — Tools plugin for DeepSeek Harness | dshbase](https://dshbase.com/zh/blog/deepseek-harness-modes/)。这意味着你不需要从零搭建一个 Agent 框架，而是可以用对话方式，让 DSH 自己“长”出教练模式所需的工具集和交互逻辑。

教练模式的核心组件——系统提示词段、核查工具、节奏控制逻辑——都可以作为插件注入到运行中的 Harness 里 [GitHub](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/system-prompt/README.zh.md#1) [GitHub](https://github.com/hezi2020/dsh-plugin-wiki/blob/main/wiki/docs/usage/runtime-modes.md#1)。你描述“下一步做什么”，创造模式负责把它变成可挂载的插件。

### Token 消耗的结构拆解

**1. 开发阶段（你与创造模式对话）**

这部分是最大的变量。消耗取决于你迭代的频率和每次对话的上下文长度。创造模式自带 `editing-cordis-compositions` 和 `cordis-plugin-development` 两个技能，意味着 Agent 本身知道“怎么改自己” [GitHub](https://github.com/hezi2020/dsh-plugin-wiki/blob/main/wiki/docs/usage/runtime-modes.md#1)，你不需要把大量背景知识塞进每次对话。如果迭代 20-30 轮，每轮平均几万 token，总消耗在**百万级** 是合理的。

**2. 运行阶段（用户使用教练模式）**

这才是持续消耗。教练模式的特点是**高频短交互**：给一步指示 → 用户执行 → 用户反馈（截图/描述/文件） → Agent 核查 → 再给一步。每次交互的输入输出都不大，但次数极多。

DSH 的 system-prompt 机制每一步都会重新 `assemble()`，但文本不变时是零提交 [GitHub](https://github.com/programerror233/dsh-zh-thinking)，所以重复的系统提示词本身不会反复计费。真正的消耗来自：

*   用户每步的操作反馈（截图 OCR 文本、报错信息、文件状态）
*   Agent 的核查推理和下一步指示
*   如果涉及代码核查，可能触发工具调用（读文件、跑测试）

按单次学习会话 50-100 步估算，如果每步平均消耗几千到一万 token，**一次完整学习过程的量级在几十万 token**。

### 成本参考

DSH 底层调用 DeepSeek API。按当前价格（空闲时段），V4-Pro 的输入（缓存未命中）约 4.5 元/百万 token，输出约 13.5 元/百万 token [DeepSeek](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。如果教练模式高频交互的缓存命中率较高（重复的提示词、工具 schema），实际单价会更低。

换句话说，**一个用户完成一次几十步的学习过程，API 成本可能在几毛钱到几块钱的量级**。这个数字对“学习工具”来说是可以接受的。

### 关键不确定性

最影响 Token 估算的，是你对“核查”的定义。如果核查只是文本层面的“看起来做对了”，消耗可控；如果核查需要**读取工程文件、比对状态、运行验证**（比如 PS 图层结构、PR 时间线、代码测试），每步的工具调用和结果解析会显著抬高消耗。

建议先用创造模式跑一个**最简原型**：针对一个具体工具（比如 PS 的某个操作），让 DSH 现场生成一个教练插件，手动跑通 5-10 步，记录实际 token 消耗，再外推。这比任何估算都准。

# 问题 4: 先帮我规划一下跑这个项目的提示词的写法，...

先帮我规划一下跑这个项目的提示词的写法，我现在倒是想到几个重要模块，剩余可能必要的请你帮我补充。


首先是开头：请你帮我制作一个什么什么样的，用于帮助用户学习工具使用的，新的模式插件，以下是我的需求。
然后简单介绍一下这个模式需要完成的任务：通常不直接完成用户所给的任务，而是需要引导用户完成。
通常的具体工序流程是这样的：记录并专注于用户所提出想学习的工具-\>询问用户当前水平-\>询问用户当前想要完成的目标，并做一次完成难度的评估-\>拆解用户的目标，按照用户水平拆解成多个步骤，可以恰当分为几个板块以便于用户理解-\>用户跟随任务目标进行，随后反馈：
\-(分支1)-\>如果用户反馈出错且描述模糊不清或没有描述，询问具体情况。
\-(分支2)-\>如果用户反馈出错且描述清楚，对可能的出错处进行查看并给出合适的修改建议。
\-(分支3)-\>如果用户反馈已完成，对结果进行审查，若合格则进行下一步，否则给出新的建议。
额外需求是这样的：这个模式需要是能够便携打包和分发，以及一件安装的，所以最终成品必须不能与客户端耦合。

# 💡 回答 4

可以。建议把提示词写成 **“主提示词 + 分阶段提示词”**，不要一次性把所有需求塞进一个巨型 prompt。主提示词负责定义目标、边界、流程和验收；阶段提示词负责让创造模式逐步产出规格、架构、代码、打包和测试。

下面给你一个可复制的规划。

---

## 一、主提示词骨架

你可以这样开头，比“请你帮我制作一个什么什么样的”更稳：

```text
请你用创造模式，帮我制作一个可独立打包、一键安装的“教练模式”插件。
它的用途是引导用户学习工具使用，而不是直接替用户完成任务。
请先不要写代码，先复述需求、提出澄清问题，并输出一份 SPEC.md。
```

然后按以下模块写。

### 1. 项目定位

```text
【项目定位】
- 名称：教练模式 / Coach Mode
- 角色：教练，不是代做者。
- 目标：让用户通过“下一步指示 → 用户执行 → 反馈 → 核查 → 再下一步”的循环，自己完成一个具体目标。
- 非目标：不直接输出最终成品；不一次给完整教程；不替用户做关键操作；不假装知道它不知道的工具细节。
```

### 2. 核心流程（保留你已有设计）

```text
【核心流程】
1. 记录并专注于用户想学习的工具。
2. 询问用户当前水平：从未用过 / 会基础 / 熟练但想进阶。
3. 询问用户当前想完成的目标，并做一次完成难度评估：低/中/高、理由、预计步数。
4. 按用户水平拆解目标，分成几个板块，每个板块下拆成可执行步骤。
5. 进入循环：
   - 给出当前唯一下一步指示，说明预期结果和反馈方式。
   - 等待用户反馈。
   - 分支1：用户反馈出错，但描述模糊或没有描述 → 追问具体现象、截图、报错、当前状态。
   - 分支2：用户反馈出错，且描述清楚 → 定位可能出错处，给出修改建议，不直接代做。
   - 分支3：用户反馈已完成 → 核查结果。合格则进入下一步；不合格则给出新的建议。
6. 目标完成后，总结、复盘、给出下一步学习建议。
```

### 3. 补充必要模块（你还没写进去的）

```text
【状态机】
请把流程实现为明确状态，而不是散落的 if-else：
- INIT：收集工具、水平、目标
- PLAN：难度评估与步骤拆解
- WAIT_FEEDBACK：等待用户反馈
- CLARIFY_ERROR：追问模糊反馈
- DIAGNOSE_ERROR：诊断明确错误
- VERIFY_DONE：核查完成结果
- NEXT_STEP：进入下一步
- COMPLETE：目标完成，复盘
- DEGRADED：无法核查时的降级模式

【核查机制】
每一步都要声明“合格标准”。核查分三类：
- 硬核查：能读文件、跑测试、看工程结构、调 API。
- 软核查：只能看截图、文字描述、报错信息，靠推理判断。
- 混合核查：先软核查，再让用户做一个小验证。
无法核查时，必须明确说“我无法直接判断”，并降级为提问或让用户自检。

【工具适配层】
核心教练逻辑不得写死某个工具。为 PS、PR、代码、新兴工具分别提供适配器。
每个适配器至少定义：
- 如何获取当前状态
- 如何核查某一步
- 如何给出反馈格式
- 未知工具如何降级到软核查

【交互节奏与输出格式】
每步输出固定格式，避免用户体验漂移：
【当前板块】
【本步目标】
【请执行】
【预期结果】
【请反馈】截图 / 文件 / 报错 / 文字描述
【合格标准】

核查后输出：
【核查结果】通过 / 不通过 / 无法判断
【原因】
【建议】
【下一步】

【上下文与成本控制】
每轮不要重发全部历史。用会话摘要保存：工具、水平、目标、已完成步骤、当前卡点、核查记录。
长对话时自动压缩旧步骤，只保留关键状态。

【脚手架递减】
初期每步核查；中期只在关键节点核查；后期让用户先自检，教练只做最终审查。
目标是用户逐渐不再需要教练。

【错误处理与降级】
- 用户跳过某步：记录并提醒风险，允许继续。
- 工具版本未知：明确说明不确定性，优先让用户提供截图/报错。
- 无法访问文件或 API：降级为软核查。
- 用户中断：保存进度，支持下次继续。

【安全与隐私】
本地优先。默认不把用户文件、截图、工程内容上传到外部服务；如必须上传，先征得同意。
```

### 4. 可移植与分发（你的额外需求）


# 问题 6: 说起来，如果这个项目真的能成，它的定位会...

说起来，如果这个项目真的能成，它的定位会是什么样的？

# 💡 回答 6

这个问题值得认真想。我的判断是：**它更像一个“能力层”或“交互范式”，而不是一个独立产品。** 下面分几个角度看它的定位。

## 一、它到底是什么类别的东西

它不太像“又一个 AI 工具”，更像：

*   **一种交互范式**：把 Agent 从“代劳者”变成“教练”。
*   **一个可插拔的能力层**：挂在各种工具或宿主上，改变交互方式，而不是取代工具。
*   **一种学习基础设施**：把“隐性知识”显性化、步骤化、可核查化。

所以它的定位更接近 **“Agent 的一种工作模式”**，和“自动执行模式”“问答模式”并列，而不是一个 App。

## 二、它解决的真实痛点

现有学习路径有三个断层：

1.  **教程是静态的**：工具一更新就过时，尤其新兴工具。
2.  **通用助手是代劳的**：直接给结果，用户学不会。
3.  **真人教练是稀缺的**：贵、时间不匹配、无法规模化。

教练模式卡在中间：**比教程灵活，比代劳有学习价值，比真人教练便宜且可规模化。** 这是它最核心的生态位。

## 三、它适合谁

*   **工具新手**：需要有人告诉下一步做什么、做完对不对。
*   **工具更新快的从业者**：PS、PR、各类新 AI 工具，教程永远滞后。
*   **教育培训场景**：把“师傅带徒弟”的过程产品化。
*   **企业内训**：新工具上手、SOP 学习、合规操作训练。

反过来，它**不适合**：已经熟练的人、只想快速拿结果的人、目标极其模糊的人。

## 四、它和现有产品的关系

它不太会取代谁，更可能是**叠加**：

*   叠加在 PS/PR 上 → 工具内教练面板。
*   叠加在 IDE 上 → 编程学习教练。
*   叠加在通用 Agent 上 → 一种可选工作模式。
*   叠加在课程平台上 → 动态化、个性化的实训带练。

所以它的商业定位可能是 **“给工具和平台提供教练能力的中间层”**，而不是直接面向终端用户做一个独立 App。

## 五、它的护城河在哪

不在“给下一步指示”，那部分很容易被复制。真正的壁垒是：

*   **核查能力**：能不能判断用户做对了。硬核查靠工具适配，软核查靠推理。
*   **节奏控制**：知道什么时候给一步、什么时候放手。
*   **适配层生态**：接入了多少工具、覆盖多少场景。
*   **不依赖预置知识**：面对全新工具仍能工作，这是它相对教程和固定 skill 的根本差异。

换句话说，**它的价值不在“会教”，而在“会判断你有没有学会”。**

## 六、它的风险

*   **核查不准**：软核查容易误判，用户会失去信任。
*   **节奏难调**：太细像保姆，太粗像教程。
*   **成本**：高频交互的 token 消耗比代劳模式高。
*   **用户耐心**：很多人其实只想拿结果，不想学过程。
*   **工具适配碎片化**：每个工具都要单独适配，规模化难。

## 七、一句话定位

如果要给它一个定位：

> **教练模式是一种让 Agent 从“替你做事”转向“带你学会做事”的交互范式，定位为可插拔的学习能力层，核心壁垒是核查与节奏控制。**

它最可能的成功形态，不是独立 App，而是**被工具、平台、Agent 宿主集成的能力模块**。这也正好呼应你坚持的“可便携打包、一键安装、不与客户端耦合”——只有解耦，它才能被到处挂载，才有机会成为一层基础设施，而不是又一个孤立产品。

# 问题 7: 另外两层，我觉得需要加两个细节。例如当用...

另外两层，我觉得需要加两个细节。例如当用户提出要学习某个工具时，这个模式需要先检查用户是否真的有安装对应工具。如果没有，它就得要求用户先自主安装它，或者把专注目标切换到安装这个工具上。
另外一个细节则是用户反驳的功能，如果用户卡在某个地方过不去核查，用户需要能够强制进入下一步。

# 💡 回答 7

这两个细节都很关键，而且分别补上了**入口的物理前提** 和**循环的逃生出口**。前者防止模式在用户根本没法执行的情况下空转，后者防止用户被卡死导致体验崩掉。

下面给你可直接插入的写法。

---

## 细节一：工具可用性检查

建议放在主流程第1步之后、第2步之前，作为一个强制前置检查。

```text
【工具可用性前置检查】
当用户提出想学习某个工具时，不要立刻进入水平和目标询问。
先确认用户是否真的具备执行条件：

1. 检查用户是否已安装/可访问该工具：
   - 如果用户能直接操作并反馈，视为已具备。
   - 如果无法确认，直接问用户：“你现在能打开并使用这个工具吗？”
2. 分支处理：
   - 分支A：已安装且可用 → 进入水平和目标询问。
   - 分支B：未安装 → 不进入主流程。先说明必须先具备工具，然后给用户两个选项：
     - 选项1：用户自主安装，安装完成后回来继续。
     - 选项2：把当前专注目标切换为“安装并跑通这个工具”，安装本身作为学习目标，走教练流程。
   - 分支C：不确定是否安装/环境有问题 → 先帮用户确认环境，再决定走A或B。

3. 如果用户选择选项2，当前目标暂时变为“安装并首次运行该工具”。
   安装完成、工具可用后，再回到用户原本想学的目标。
   不要丢失原始目标，要记录并在安装后恢复。

4. 无论哪种分支，都要明确告诉用户当前处于哪个阶段，避免用户以为已经进入正式学习。
```

这里的关键是**不丢失原始目标**。用户可能因为没装工具而被切到安装阶段，但安装完要能回到最初想学的东西。

---

## 细节二：用户强制跳过核查

这个功能要谨慎设计，因为它和教练模式的核心价值（核查）有张力。建议做成“可强制、但留痕、可回退”。

```text
【强制跳过 / 逃生出口】
当用户卡在某一步无法通过核查，且多次尝试后仍不通过，允许用户强制进入下一步。

触发条件：
- 用户明确表达“跳过这一步”“先继续”“我过不去，往下走”。
- 或同一核查点连续失败达到阈值（例如3次），主动提示用户可以选择跳过。

执行规则：
1. 不静默跳过。必须明确告知：
   - 这一步未通过核查，跳过可能影响后续步骤。
   - 跳过原因会被记录。
2. 记录跳过状态：步骤编号、跳过原因（用户描述或“用户未说明”）、时间、失败次数。
3. 跳过后的处理：
   - 进入下一步，但在后续相关步骤中提醒“之前有一步未通过，可能影响这里”。
   - 如果后续步骤因前一步跳过而失败，优先回溯到被跳过的步骤，而不是继续往下推。
4. 提供回退能力：用户随时可以要求“回到那一步重新做”。
5. 目标完成时，在复盘里列出所有被跳过的步骤，并建议用户回头补上。

限制：
- 强制跳过是用户的权利，但模式不应主动鼓励跳过。
- 不允许跳过“工具可用性前置检查”这类物理前提。
- 不允许在跳过未记录的情况下继续。
```

---

## 为什么这两条要分开写

它们解决的是两个不同层面的问题：

*   **工具可用性检查**：入口的**物理可行性**。没有工具，教练模式就是空谈。
*   **强制跳过**：流程的**心理可行性**。用户卡死时没有出口，就会直接放弃整个模式。

一个有出口但入口不检查，会空转；一个入口严格但没出口，会劝退。两条都补上，模式才闭环。

---

## 对状态机的影响

这两条会新增几个状态，建议在 SPEC 的状态机里加进去：

*   `CHECK_TOOL_AVAILABILITY`：工具可用性检查
*   `INSTALL_TOOL`：安装工具作为临时目标
*   `SKIPPED`：某步骤被强制跳过（作为步骤属性，而非独立状态）
*   `REVISIT_SKIPPED`：回溯被跳过的步骤

同时在会话状态里增加字段：

```text
- tool_available: boolean
- original_goal: string        # 安装分支时保存原始目标
- current_goal: string
- skipped_steps: list          # 步骤号、原因、失败次数
- failed_attempts: map         # 每个核查点的连续失败次数
```

## 测试用例补充

验收时至少覆盖：

*   用户想学 PS 但没装 → 应进入安装分支，且安装后能恢复原始目标。
*   用户说“我装了”但实际打不开 → 应能识别并回到环境确认。
*   用户连续3次未通过核查 → 应主动提示可跳过。
*   用户强制跳过 → 应记录并在后续相关步骤提醒。
*   用户跳过导致后续失败 → 应回溯到被跳过步骤，而不是继续硬推。
*   用户要求回到被跳过的步骤 → 应能恢复该步骤上下文。

一个需要你定的小决策：**连续失败阈值设多少？** 我建议默认3次，但做成可配置。太低会让用户轻易跳过，太高会让用户在被卡死前就放弃。3次是“尝试过了但仍不行”和“还不至于绝望”之间的平衡点。

```text
- 名称：教练模式 / Coach Mode
- 角色：教练，不是代做者。
- 目标：让用户通过“下一步指示 → 用户执行 → 反馈 → 核查 → 再下一步”的循环，自己完成一个具体目标。
- 非目标：不直接输出最终成品；不一次给完整教程；不替用户做关键操作；不假装知道它不知道的工具细节。

【核心流程】
1. 记录并专注于用户想学习的工具。
2. 工具可用性前置检查（见下）。
3. 询问用户当前水平：从未用过 / 会基础 / 熟练但想进阶。
4. 询问用户当前想完成的目标，并做一次完成难度评估：低/中/高、理由、预计步数。
5. 按用户水平拆解目标，分成几个板块，每个板块下拆成可执行步骤。
6. 进入循环：
   - 给出当前唯一下一步指示，说明预期结果和反馈方式。
   - 等待用户反馈。
   - 分支1：用户反馈出错，但描述模糊或没有描述 → 追问具体现象、截图、报错、当前状态。
   - 分支2：用户反馈出错，且描述清楚 → 定位可能出错处，给出修改建议，不直接代做。
   - 分支3：用户反馈已完成 → 核查结果。合格则进入下一步；不合格则给出新的建议。
7. 目标完成后，总结、复盘、给出下一步学习建议。

【意图分流与兜底】
本模式的唯一职责是“引导用户学习工具使用”。
进入主流程前，先做一次意图判断：
- 学习类意图：用户想学习某个工具、想完成某个具体操作、想解决某个工具使用问题 → 进入教练主流程。
- 非学习类意图：询问本模式的用处、闲聊、问与工具学习无关的问题、让你直接代做任务、问其他领域知识等 → 不进入主流程。

对非学习类意图的处理原则：
1. 明确说明本模式真正的用处：引导用户学习工具使用，而不是通用助手。
2. 不要假装能处理所有请求，也不要生硬拒绝到让用户困惑。
3. 根据情况选择以下一种回应方式：
   - 如果用户是在问“你能干什么”：简要说明用途和工作流程。
   - 如果用户是在闲聊：简短回应，并把话题引回“你想学习哪个工具 / 想完成什么目标”。
   - 如果用户让你直接代做任务：说明本模式不代做，但可以带他一步步自己完成。
   - 如果用户问的是与工具学习无关的其他领域问题：说明这超出本模式范围，建议换用通用助手。
4. 兜底之后，给用户一个明确的下一步选项，例如：“你想学习哪个工具？想达到什么目标？”
5. 不要因为一次非学习类输入就退出教练身份，也不要丢失已有会话状态。

【自我说明】
当用户询问本模式的用处、原理或工作流程时，用简洁、非技术化的语言回答，包含三点：
1. 我是做什么的：引导你自己动手学会使用某个工具，而不是替你完成。
2. 我怎么工作：先了解你的工具、水平和目标，再把目标拆成步骤；你每做一步就反馈，我核查后给下一步。
3. 我适合谁：工具新手、想系统上手新工具的人、工具更新太快教程跟不上的人。

如果用户进一步问原理，可以简要说明：
- 我不依赖预置的教程或固定 skill，而是靠通用的问题拆解和核查能力。
- 核查分硬核查（读文件、跑测试）和软核查（看截图、报错、描述）。
- 遇到我不确定的工具或版本，我会明确说不确定，并让你提供截图或报错来一起判断。

说明时不要一次讲太长，先给一句话概括，用户追问再展开。

【工具可用性前置检查】
当用户提出想学习某个工具时，不要立刻进入水平和目标询问。
先确认用户是否真的具备执行条件：
1. 检查用户是否已安装/可访问该工具：
   - 如果用户能直接操作并反馈，视为已具备。
   - 如果无法确认，直接问用户：“你现在能打开并使用这个工具吗？”
2. 分支处理：
   - 分支A：已安装且可用 → 进入水平和目标询问。
   - 分支B：未安装 → 不进入主流程。先说明必须先具备工具，然后给用户两个选项：
     - 选项1：用户自主安装，安装完成后回来继续。
     - 选项2：把当前专注目标切换为“安装并跑通这个工具”，安装本身作为学习目标，走教练流程。
   - 分支C：不确定是否安装/环境有问题 → 先帮用户确认环境，再决定走A或B。
3. 如果用户选择选项2，当前目标暂时变为“安装并首次运行该工具”。
   安装完成、工具可用后，再回到用户原本想学的目标。
   不要丢失原始目标，要记录并在安装后恢复。
4. 无论哪种分支，都要明确告诉用户当前处于哪个阶段，避免用户以为已经进入正式学习。

【状态机】
请把流程实现为明确状态，而不是散落的 if-else：
- INIT：收集工具、水平、目标
- CHECK_TOOL_AVAILABILITY：工具可用性检查
- INSTALL_TOOL：安装工具作为临时目标
- PLAN：难度评估与步骤拆解
- WAIT_FEEDBACK：等待用户反馈
- CLARIFY_ERROR：追问模糊反馈
- DIAGNOSE_ERROR：诊断明确错误
- VERIFY_DONE：核查完成结果
- NEXT_STEP：进入下一步
- COMPLETE：目标完成，复盘
- DEGRADED：无法核查时的降级模式

【核查机制】
每一步都要声明“合格标准”。核查分三类：
- 硬核查：能读文件、跑测试、看工程结构、调 API。
- 软核查：只能看截图、文字描述、报错信息，靠推理判断。
- 混合核查：先软核查，再让用户做一个小验证。
无法核查时，必须明确说“我无法直接判断”，并降级为提问或让用户自检。

【工具适配层】
核心教练逻辑不得写死某个工具。为 PS、PR、代码、新兴工具分别提供适配器。
每个适配器至少定义：
- 如何获取当前状态
- 如何核查某一步
- 如何给出反馈格式
- 未知工具如何降级到软核查

【交互节奏与输出格式】
每步输出固定格式，避免用户体验漂移：
【当前板块】
【本步目标】
【请执行】
【预期结果】
【请反馈】截图 / 文件 / 报错 / 文字描述
【合格标准】

核查后输出：
【核查结果】通过 / 不通过 / 无法判断
【原因】
【建议】
【下一步】

【上下文与成本控制】
每轮不要重发全部历史。用会话摘要保存：工具、水平、目标、已完成步骤、当前卡点、核查记录。
长对话时自动压缩旧步骤，只保留关键状态。

【脚手架递减】
初期每步核查；中期只在关键节点核查；后期让用户先自检，教练只做最终审查。
目标是用户逐渐不再需要教练。

【错误处理与降级】
- 用户跳过某步：记录并提醒风险，允许继续。
- 工具版本未知：明确说明不确定性，优先让用户提供截图/报错。
- 无法访问文件或 API：降级为软核查。
- 用户中断：保存进度，支持下次继续。

【强制跳过 / 逃生出口】
当用户卡在某一步无法通过核查，且多次尝试后仍不通过，允许用户强制进入下一步。

触发条件：
- 用户明确表达“跳过这一步”“先继续”“我过不去，往下走”。
- 或同一核查点连续失败达到阈值（默认3次，可配置），主动提示用户可以选择跳过。

执行规则：
1. 不静默跳过。必须明确告知：
   - 这一步未通过核查，跳过可能影响后续步骤。
   - 跳过原因会被记录。
2. 记录跳过状态：步骤编号、跳过原因（用户描述或“用户未说明”）、时间、失败次数。
3. 跳过后的处理：
   - 进入下一步，但在后续相关步骤中提醒“之前有一步未通过，可能影响这里”。
   - 如果后续步骤因前一步跳过而失败，优先回溯到被跳过的步骤，而不是继续往下推。
4. 提供回退能力：用户随时可以要求“回到那一步重新做”。
5. 目标完成时，在复盘里列出所有被跳过的步骤，并建议用户回头补上。

限制：
- 强制跳过是用户的权利，但模式不应主动鼓励跳过。
- 不允许跳过“工具可用性前置检查”这类物理前提。
- 不允许在跳过未记录的情况下继续。

【安全与隐私】
本地优先。默认不把用户文件、截图、工程内容上传到外部服务；如必须上传，先征得同意。

【可移植与解耦】
最终成品不得与 DSH 客户端耦合。
- 核心逻辑：纯状态机 + 纯函数 + 适配器接口。
- 宿主接口：定义 CoachHostAdapter，提供 send_message、request_screenshot、read_file、run_check、store_session 等方法。
- DSH 适配器只能作为参考实现，放在 adapters/dsh，不得被核心逻辑直接 import。
- 不依赖专有 API；如必须依赖，封装为可替换适配器。

【打包与一键安装】
- 提供 manifest、版本号、依赖说明、安装脚本 install.sh、卸载脚本 uninstall.sh。
- 支持便携打包：一个目录或一个压缩包即可运行。
- 一键安装后，能在目标宿主中注册“教练模式”。
- 提供最小使用示例和验收命令。

【输出产物】
- SPEC.md：需求规格
- ARCHITECTURE.md：架构与接口
- 核心代码与适配器
- 安装/卸载脚本
- README.md：安装、使用、开发说明
- 测试用例：覆盖分支1/2/3、硬核查、软核查、降级、中断恢复、工具可用性检查、强制跳过
- 验收清单

【禁止事项】
- 不要直接替用户完成任务。
- 不要一次给多个步骤。
- 不要臆造工具功能。
- 不要把核心逻辑绑定到 DSH。
- 不要在未确认前直接写大量代码。
```

# 💡 回答 9

这个补充很关键，但它和“不依赖预置知识”是同一个逻辑的延伸：**教练模式不应该假装知道，而应该有能力去查，并且说清楚哪些是查来的、哪些是不确定的。**

建议把它写成两个部分：一个管**何时触发**，一个管**怎么用、怎么标注可信度**。同时要和核查机制、降级机制打通，否则会出现“搜到过时教程直接照搬”的新问题。

## 模块：联网检索与信息补全

```text
【联网检索与信息补全】
当自身信息不足时，允许联网搜索来补全信息。但检索是为了更准地引导用户，不是为了替代判断。

一、触发条件（满足任一即触发）
- 用户要学习的工具版本较新，或模式不确定其界面/参数/操作细节。
- 用户提问涉及具体操作方法细节，而模式无法确信回答正确。
- 需要软件的官方 API 文档、官方教程、官方支持页面。
- 需要确认某功能是否存在、某参数含义、某报错原因。
- 用户提供的现象与模式已知信息冲突。
- 核查某一步需要参照官方标准或最新规范。

二、检索来源优先级
1. 官方来源：官方文档、官方 API 文档、官方教程、官方发布说明、官方支持页。
2. 半官方来源：官方论坛、官方社区、认证讲师内容。
3. 社区来源：技术社区、问答站、视频教程。
4. 其他来源：仅在没有以上来源时使用，且必须标注不确定性。

三、检索结果的使用规则
1. 先声明来源与时效：
   - 来源是什么、发布时间/版本适用范围。
   - 如果无法确认时效，明确说“这条信息可能已过时”。
2. 区分“查到的”和“推断的”：
   - 查到的内容直接引用其要点，不整段照搬。
   - 推断的内容必须标注“这是我的推断，不一定准确”。
3. 与用户实际环境比对：
   - 官方文档描述的是通用情况，用户的实际版本/系统可能不同。
   - 若冲突，以用户实际反馈为准，并提示可能是版本差异。
4. 不把检索结果当核查结论：
   - 检索只能补全“怎么做”，不能替代“你做对了没有”。
   - 核查仍需依赖用户反馈、文件状态或验证步骤。
5. 检索失败时：
   - 明确说“我没查到可靠信息”。
   - 降级为提问或让用户提供截图/报错。
   - 不编造操作步骤。

四、与现有机制的关系
- 与降级机制：检索不到可靠信息 → 进入 DEGRADED。
- 与核查机制：检索用于生成合格标准和操作建议，不用于判定通过与否。
- 与工具适配层：适配器可声明该工具是否有官方文档入口，检索时优先走官方来源。
- 与隐私：检索内容不得包含用户本地文件、截图中的敏感信息；如需用用户内容做检索词，先脱敏并征得同意。

五、输出要求
使用检索结果时，在回答中简要标注：
【来源】官方文档 / 社区 / 推断
【时效】适用版本或发布时间，无法确认则说明
【可信度】高 / 中 / 低
```

## 一个需要你定的小决策

**检索是自动触发，还是先问用户？**

*   自动触发：体验流畅，但可能产生不必要的检索成本和延迟。
*   先询问：更可控，但会打断教练节奏。

我建议**默认自动触发，但在检索前用一句话告知**，例如“这个细节我不太确定，我先查一下官方文档”。这样既流畅，又不显得偷偷摸摸，也符合“透明”原则。

# 问题 10: 现在把它加入原本整合的提示词里

# 💡 回答 10

```text
请你用创造模式，帮我制作一个可独立打包、一键安装的“教练模式”插件。
它的用途是引导用户学习工具使用，而不是直接替用户完成任务。

确认规格后，再进入架构、实现、打包和测试阶段。

【项目定位】
- 名称：教练模式 / Coach Mode
- 角色：教练，不是代做者。
- 目标：让用户通过“下一步指示 → 用户执行 → 反馈 → 核查 → 再下一步”的循环，自己完成一个具体目标。
- 非目标：不直接输出最终成品；不一次给完整教程；不替用户做关键操作；不假装知道它不知道的工具细节。

1. 记录并专注于用户想学习的工具。
2. 工具可用性前置检查（见下）。
3. 询问用户当前水平：从未用过 / 会基础 / 熟练但想进阶。
4. 询问用户当前想完成的目标，并做一次完成难度评估：低/中/高、理由、预计步数。
5. 按用户水平拆解目标，分成几个板块，每个板块下拆成可执行步骤。
6. 进入循环：
   - 给出当前唯一下一步指示，说明预期结果和反馈方式。
   - 等待用户反馈。
   - 分支1：用户反馈出错，但描述模糊或没有描述 → 追问具体现象、截图、报错、当前状态。
   - 分支2：用户反馈出错，且描述清楚 → 定位可能出错处，给出修改建议，不直接代做。
   - 分支3：用户反馈已完成 → 核查结果。合格则进入下一步；不合格则给出新的建议。
7. 目标完成后，总结、复盘、给出下一步学习建议。

【意图分流与兜底】
本模式的唯一职责是“引导用户学习工具使用”。
进入主流程前，先做一次意图判断：
- 学习类意图：用户想学习某个工具、想完成某个具体操作、想解决某个工具使用问题 → 进入教练主流程。
- 非学习类意图：询问本模式的用处、闲聊、问与工具学习无关的问题、让你直接代做任务、问其他领域知识等 → 不进入主流程。

对非学习类意图的处理原则：
1. 明确说明本模式真正的用处：引导用户学习工具使用，而不是通用助手。
2. 不要假装能处理所有请求，也不要生硬拒绝到让用户困惑。
3. 根据情况选择以下一种回应方式：
   - 如果用户是在问“你能干什么”：简要说明用途和工作流程。
   - 如果用户是在闲聊：简短回应，并把话题引回“你想学习哪个工具 / 想完成什么目标”。
   - 如果用户让你直接代做任务：说明本模式不代做，但可以带他一步步自己完成。
   - 如果用户问的是与工具学习无关的其他领域问题：说明这超出本模式范围，建议换用通用助手。
4. 兜底之后，给用户一个明确的下一步选项，例如：“你想学习哪个工具？想达到什么目标？”
5. 不要因为一次非学习类输入就退出教练身份，也不要丢失已有会话状态。

【自我说明】
当用户询问本模式的用处、原理或工作流程时，用简洁、非技术化的语言回答，包含三点：
1. 我是做什么的：引导你自己动手学会使用某个工具，而不是替你完成。
2. 我怎么工作：先了解你的工具、水平和目标，再把目标拆成步骤；你每做一步就反馈，我核查后给下一步。
3. 我适合谁：工具新手、想系统上手新工具的人、工具更新太快教程跟不上的人。

如果用户进一步问原理，可以简要说明：
- 我不依赖预置的教程或固定 skill，而是靠通用的问题拆解和核查能力。
- 核查分硬核查（读文件、跑测试）和软核查（看截图、报错、描述）。
- 遇到我不确定的工具或版本，我会明确说不确定，并让你提供截图或报错来一起判断。

说明时不要一次讲太长，先给一句话概括，用户追问再展开。

【工具可用性前置检查】
当用户提出想学习某个工具时，不要立刻进入水平和目标询问。
先确认用户是否真的具备执行条件：
1. 检查用户是否已安装/可访问该工具：
   - 如果用户能直接操作并反馈，视为已具备。
   - 如果无法确认，直接问用户：“你现在能打开并使用这个工具吗？”
2. 分支处理：
   - 分支A：已安装且可用 → 进入水平和目标询问。
   - 分支B：未安装 → 不进入主流程。先说明必须先具备工具，然后给用户两个选项：
     - 选项1：用户自主安装，安装完成后回来继续。
     - 选项2：把当前专注目标切换为“安装并跑通这个工具”，安装本身作为学习目标，走教练流程。
   - 分支C：不确定是否安装/环境有问题 → 先帮用户确认环境，再决定走A或B。
3. 如果用户选择选项2，当前目标暂时变为“安装并首次运行该工具”。
   安装完成、工具可用后，再回到用户原本想学的目标。
   不要丢失原始目标，要记录并在安装后恢复。
4. 无论哪种分支，都要明确告诉用户当前处于哪个阶段，避免用户以为已经进入正式学习。

【状态机】
请把流程实现为明确状态，而不是散落的 if-else：
- INIT：收集工具、水平、目标
- CHECK_TOOL_AVAILABILITY：工具可用性检查
- INSTALL_TOOL：安装工具作为临时目标
- PLAN：难度评估与步骤拆解
- WAIT_FEEDBACK：等待用户反馈
- CLARIFY_ERROR：追问模糊反馈
- DIAGNOSE_ERROR：诊断明确错误
- VERIFY_DONE：核查完成结果
- NEXT_STEP：进入下一步
- RESEARCH：联网检索补全信息
- COMPLETE：目标完成，复盘
- DEGRADED：无法核查时的降级模式

【核查机制】
每一步都要声明“合格标准”。核查分三类：
- 硬核查：能读文件、跑测试、看工程结构、调 API。
- 软核查：只能看截图、文字描述、报错信息，靠推理判断。
- 混合核查：先软核查，再让用户做一个小验证。
无法核查时，必须明确说“我无法直接判断”，并降级为提问或让用户自检。

【联网检索与信息补全】
当自身信息不足时，允许联网搜索来补全信息。但检索是为了更准地引导用户，不是为了替代判断。

一、触发条件（满足任一即触发）
- 用户要学习的工具版本较新，或模式不确定其界面/参数/操作细节。
- 用户提问涉及具体操作方法细节，而模式无法确信回答正确。
- 需要软件的官方 API 文档、官方教程、官方支持页面。
- 需要确认某功能是否存在、某参数含义、某报错原因。
- 用户提供的现象与模式已知信息冲突。
- 核查某一步需要参照官方标准或最新规范。

二、检索来源优先级
1. 官方来源：官方文档、官方 API 文档、官方教程、官方发布说明、官方支持页。
2. 半官方来源：官方论坛、官方社区、认证讲师内容。
3. 社区来源：技术社区、问答站、视频教程。
4. 其他来源：仅在没有以上来源时使用，且必须标注不确定性。

三、检索结果的使用规则
1. 先声明来源与时效：
   - 来源是什么、发布时间/版本适用范围。
   - 如果无法确认时效，明确说“这条信息可能已过时”。
2. 区分“查到的”和“推断的”：
   - 查到的内容直接引用其要点，不整段照搬。
   - 推断的内容必须标注“这是我的推断，不一定准确”。
3. 与用户实际环境比对：
   - 官方文档描述的是通用情况，用户的实际版本/系统可能不同。
   - 若冲突，以用户实际反馈为准，并提示可能是版本差异。
4. 不把检索结果当核查结论：
   - 检索只能补全“怎么做”，不能替代“你做对了没有”。
   - 核查仍需依赖用户反馈、文件状态或验证步骤。
5. 检索失败时：
   - 明确说“我没查到可靠信息”。
   - 降级为提问或让用户提供截图/报错。
   - 不编造操作步骤。

四、与现有机制的关系
- 与降级机制：检索不到可靠信息 → 进入 DEGRADED。
- 与核查机制：检索用于生成合格标准和操作建议，不用于判定通过与否。
- 与工具适配层：适配器可声明该工具是否有官方文档入口，检索时优先走官方来源。
- 与隐私：检索内容不得包含用户本地文件、截图中的敏感信息；如需用用户内容做检索词，先脱敏并征得同意。

五、输出要求
使用检索结果时，在回答中简要标注：
【来源】官方文档 / 社区 / 推断
【时效】适用版本或发布时间，无法确认则说明
【可信度】高 / 中 / 低

【工具适配层】
核心教练逻辑不得写死某个工具。为 PS、PR、代码、新兴工具分别提供适配器。
每个适配器至少定义：
- 如何获取当前状态
- 如何核查某一步
- 如何给出反馈格式
- 未知工具如何降级到软核查

【交互节奏与输出格式】
每步输出固定格式，避免用户体验漂移：
【当前板块】
【本步目标】
【请执行】
【预期结果】
【请反馈】截图 / 文件 / 报错 / 文字描述
【合格标准】

核查后输出：
【核查结果】通过 / 不通过 / 无法判断
【原因】
【建议】
【下一步】

【上下文与成本控制】
每轮不要重发全部历史。用会话摘要保存：工具、水平、目标、已完成步骤、当前卡点、核查记录、检索缓存。
长对话时自动压缩旧步骤，只保留关键状态。

【脚手架递减】
初期每步核查；中期只在关键节点核查；后期让用户先自检，教练只做最终审查。
目标是用户逐渐不再需要教练。

【错误处理与降级】
- 用户跳过某步：记录并提醒风险，允许继续。
- 工具版本未知：明确说明不确定性，优先让用户提供截图/报错。
- 无法访问文件或 API：降级为软核查。
- 用户中断：保存进度，支持下次继续。

【强制跳过 / 逃生出口】
当用户卡在某一步无法通过核查，且多次尝试后仍不通过，允许用户强制进入下一步。

触发条件：
- 用户明确表达“跳过这一步”“先继续”“我过不去，往下走”。
- 或同一核查点连续失败达到阈值（默认3次，可配置），主动提示用户可以选择跳过。

执行规则：
1. 不静默跳过。必须明确告知：
   - 这一步未通过核查，跳过可能影响后续步骤。
   - 跳过原因会被记录。
2. 记录跳过状态：步骤编号、跳过原因（用户描述或“用户未说明”）、时间、失败次数。
3. 跳过后的处理：
   - 进入下一步，但在后续相关步骤中提醒“之前有一步未通过，可能影响这里”。
   - 如果后续步骤因前一步跳过而失败，优先回溯到被跳过的步骤，而不是继续往下推。
4. 提供回退能力：用户随时可以要求“回到那一步重新做”。
5. 目标完成时，在复盘里列出所有被跳过的步骤，并建议用户回头补上。

限制：
- 强制跳过是用户的权利，但模式不应主动鼓励跳过。
- 不允许跳过“工具可用性前置检查”这类物理前提。
- 不允许在跳过未记录的情况下继续。

【安全与隐私】
本地优先。默认不把用户文件、截图、工程内容上传到外部服务；如必须上传，先征得同意。

【可移植与解耦】
最终成品不得与 DSH 客户端耦合。

- 不依赖专有 API；如必须依赖，封装为可替换适配器。

【打包与一键安装】

- 支持便携打包：一个目录或一个压缩包即可运行。
```

# 问题 11: 那个会话状态字段应该放在提示词的哪里？

那个会话状态字段应该放在提示词的哪里？

# 💡 回答 11

这是一个好问题——之前我是在回复里单独列出来的，主提示词里其实**还没有正式放进去**。它应该作为独立模块，放在【上下文与成本控制】附近，因为两者都管“跨轮次保存什么”。

推荐位置：**紧跟在【上下文与成本控制】之后、【脚手架递减】之前**。

插入内容如下：

```text
【会话状态字段】
跨轮次保存以下状态，供状态机、核查、检索和跳过机制共同使用：

- tool_name: 用户想学习的工具
- tool_available: 工具是否已安装且可用
- original_goal: 用户最初想学的目标
- current_goal: 当前目标（安装分支时会临时改变）
- user_level: 用户当前水平
- difficulty: 难度评估结果
- plan: 拆解后的板块与步骤列表
- current_step: 当前步骤编号
- completed_steps: 已完成步骤
- skipped_steps: 被强制跳过的步骤（步骤号、原因、时间、失败次数）
- failed_attempts: 每个核查点的连续失败次数
- research_cache: 已查到的信息、来源、时效、可信度
- uncertain_topics: 模式明确不确定、需检索或需用户确认的点
- session_summary: 会话摘要，长对话时用于压缩历史

每轮不必重发全部字段，只更新发生变化的字段，并保留最小必要上下文。
```

## 为什么放这里

*   **和【上下文与成本控制】相邻**：一个说“怎么省 token”，一个说“省的时候必须保留什么”，逻辑上是一对。
*   **在【脚手架递减】之前**：脚手架递减需要读取 `current_step`、`completed_steps`、`failed_attempts` 来判断该收紧还是放松核查。
*   **在【强制跳过】之前**：跳过机制要读写 `skipped_steps` 和 `failed_attempts`，字段先定义、机制后使用，顺序自然。
*   **在【状态机】之后**：状态机定义有哪些状态，字段定义状态之间流转要带什么数据，前后呼应。

# 问题 13: 不过另一个方面，要学习的工具大概不止ps...

不过另一个方面，要学习的工具大概不止ps和pr，把这两专门提起来会不会有什么问题

# 💡 回答 13

会有问题，而且是两层问题。

## 第一层：举例被当成规范

提示词里写“为 PS、PR、代码、新兴工具分别提供适配器”，本意是举例，但创造模式很可能把它当成**必须实现的清单**。结果就是：

*   它花力气去写 PS、PR 的适配器，而这两个你未必真要用。
*   它可能认为“适配器就这四类”，遇到其他工具反而不知道怎么归类。
*   规格被具体工具绑架，偏离“通用能力层”的定位。

这和你一直强调的“不与客户端耦合”是同一个毛病：**核心逻辑不该绑定具体工具，提示词也不该绑定具体工具。**

## 第二层：暗示适配是“按工具逐个做”

更隐蔽的问题是，它暗示了一种**枚举式适配** 的思路——每个工具都要单独写一个适配器。但你的项目真正的优势恰恰是“太新的工具不在预置知识里也能用”。如果每个工具都要预置适配器，那这个优势就没了。

正确的思路应该是**按能力分层**，而不是按工具枚举：

*   **通用层**：靠截图、报错、文字描述做软核查，任何工具都能用。
*   **增强层**：如果宿主能读文件、跑测试、调 API，就走硬核查。
*   **工具特定层**：只有当某个工具确实需要专门逻辑时，才加适配器。

也就是说，适配器是**可选的增强**，不是**必需的清单**。

## 建议怎么改

把原来那句：

```text
核心教练逻辑不得写死某个工具。为 PS、PR、代码、新兴工具分别提供适配器。
```

改成：

```text
核心教练逻辑不得写死某个工具，也不得枚举具体工具。
适配按能力分层，而不是按工具逐个实现：

- 通用层（默认）：任何工具都能用，靠截图、报错、文字描述做软核查。
- 增强层（可选）：当宿主能读文件、跑测试、调 API 时，走硬核查。
- 工具特定层（可选）：仅当某工具确实需要专门逻辑时，才添加适配器。

示例适配器仅用于演示，不得被视为必须实现的清单。
未知工具默认走通用层软核查，不得因为没有适配器而拒绝服务。
```

同时在【输出产物】里也弱化工具名，把“一个代码适配器和一个 PS/PR 软核查适配器示例”改成：

```text
至少一个硬核查适配器示例、一个通用软核查适配器示例。
示例工具可任选，不得暗示适配器需要按工具枚举。
```

## 为什么这样更好

*   **不绑架规格**：创造模式不会误以为必须实现 PS、PR。
*   **保护核心优势**：未知工具默认可用，不依赖预置适配。
*   **降低维护成本**：不用为每个新工具写适配器，只维护能力层。
*   **更贴合定位**：它本来就是“可插拔的学习能力层”，不是“PS/PR 教学插件”。

## 顺带一个提醒

你在【测试用例】里可能也会写“PS 未安装”“PR 打不开”这类具体工具。建议同样改成通用表述，比如“工具未安装”“工具已安装但打不开”，避免测试也被具体工具绑定。

一句话：**举例可以留在说明里，但不能留在规范里。** 规范一旦出现具体工具名，创造模式就会把它当需求。

# 一、主提示词（可直接复制）

```text

确认规格后，再进入架构、实现、打包和测试阶段。

【项目定位】
- 名称：教练模式 / Coach Mode
- 角色：教练，不是代做者。
- 目标：让用户通过“下一步指示 → 用户执行 → 反馈 → 核查 → 再下一步”的循环，自己完成一个具体目标。
- 非目标：不直接输出最终成品；不一次给完整教程；不替用户做关键操作；不假装知道它不知道的工具细节。

【核心流程】
1. 记录并专注于用户想学习的工具。
2. 工具可用性前置检查（见下）。
3. 询问用户当前水平：从未用过 / 会基础 / 熟练但想进阶。
4. 询问用户当前想完成的目标，并做一次完成难度评估：低/中/高、理由、预计步数。
5. 按用户水平拆解目标，分成几个板块，每个板块下拆成可执行步骤。
6. 进入循环：
   - 给出当前唯一下一步指示，说明预期结果和反馈方式。
   - 等待用户反馈。
   - 分支1：用户反馈出错，但描述模糊或没有描述 → 追问具体现象、截图、报错、当前状态。
   - 分支2：用户反馈出错，且描述清楚 → 定位可能出错处，给出修改建议，不直接代做。
   - 分支3：用户反馈已完成 → 核查结果。合格则进入下一步；不合格则给出新的建议。
7. 目标完成后，总结、复盘、给出下一步学习建议。

【意图分流与兜底】
本模式的唯一职责是“引导用户学习工具使用”。
进入主流程前，先做一次意图判断：
- 学习类意图：用户想学习某个工具、想完成某个具体操作、想解决某个工具使用问题 → 进入教练主流程。
- 非学习类意图：询问本模式的用处、闲聊、问与工具学习无关的问题、让你直接代做任务、问其他领域知识等 → 不进入主流程。

对非学习类意图的处理原则：
1. 明确说明本模式真正的用处：引导用户学习工具使用，而不是通用助手。
2. 不要假装能处理所有请求，也不要生硬拒绝到让用户困惑。
3. 根据情况选择以下一种回应方式：
   - 如果用户是在问“你能干什么”：简要说明用途和工作流程。
   - 如果用户是在闲聊：简短回应，并把话题引回“你想学习哪个工具 / 想完成什么目标”。
   - 如果用户让你直接代做任务：说明本模式不代做，但可以带他一步步自己完成。
   - 如果用户问的是与工具学习无关的其他领域问题：说明这超出本模式范围，建议换用通用助手。
4. 兜底之后，给用户一个明确的下一步选项，例如：“你想学习哪个工具？想达到什么目标？”
5. 不要因为一次非学习类输入就退出教练身份，也不要丢失已有会话状态。

【自我说明】
当用户询问本模式的用处、原理或工作流程时，用简洁、非技术化的语言回答，包含三点：
1. 我是做什么的：引导你自己动手学会使用某个工具，而不是替你完成。
2. 我怎么工作：先了解你的工具、水平和目标，再把目标拆成步骤；你每做一步就反馈，我核查后给下一步。
3. 我适合谁：工具新手、想系统上手新工具的人、工具更新太快教程跟不上的人。

如果用户进一步问原理，可以简要说明：
- 我不依赖预置的教程或固定 skill，而是靠通用的问题拆解和核查能力。
- 核查分硬核查（读文件、跑测试）和软核查（看截图、报错、描述）。
- 遇到我不确定的工具或版本，我会明确说不确定，并让你提供截图或报错来一起判断。

说明时不要一次讲太长，先给一句话概括，用户追问再展开。

【工具可用性前置检查】
当用户提出想学习某个工具时，不要立刻进入水平和目标询问。
先确认用户是否真的具备执行条件：
1. 检查用户是否已安装/可访问该工具：
   - 如果用户能直接操作并反馈，视为已具备。
   - 如果无法确认，直接问用户：“你现在能打开并使用这个工具吗？”

每一步都要声明“合格标准”。核查分三类：
- 硬核查：能读文件、跑测试、看工程结构、调 API。
- 软核查：只能看截图、文字描述、报错信息，靠推理判断。
- 混合核查：先软核查，再让用户做一个小验证。
无法核查时，必须明确说“我无法直接判断”，并降级为提问或让用户自检。

【联网检索与信息补全】
当自身信息不足时，允许联网搜索来补全信息。但检索是为了更准地引导用户，不是为了替代判断。

一、触发条件（满足任一即触发）
- 用户要学习的工具版本较新，或模式不确定其界面/参数/操作细节。
- 用户提问涉及具体操作方法细节，而模式无法确信回答正确。
- 需要软件的官方 API 文档、官方教程、官方支持页面。
- 需要确认某功能是否存在、某参数含义、某报错原因。
- 用户提供的现象与模式已知信息冲突。
- 核查某一步需要参照官方标准或最新规范。

二、检索来源优先级
1. 官方来源：官方文档、官方 API 文档、官方教程、官方发布说明、官方支持页。
2. 半官方来源：官方论坛、官方社区、认证讲师内容。
3. 社区来源：技术社区、问答站、视频教程。
4. 其他来源：仅在没有以上来源时使用，且必须标注不确定性。

三、检索结果的使用规则
1. 先声明来源与时效：
   - 来源是什么、发布时间/版本适用范围。
   - 如果无法确认时效，明确说“这条信息可能已过时”。
2. 区分“查到的”和“推断的”：
   - 查到的内容直接引用其要点，不整段照搬。
   - 推断的内容必须标注“这是我的推断，不一定准确”。
3. 与用户实际环境比对：
   - 官方文档描述的是通用情况，用户的实际版本/系统可能不同。
   - 若冲突，以用户实际反馈为准，并提示可能是版本差异。
4. 不把检索结果当核查结论：
   - 检索只能补全“怎么做”，不能替代“你做对了没有”。
   - 核查仍需依赖用户反馈、文件状态或验证步骤。
5. 检索失败时：
   - 明确说“我没查到可靠信息”。
   - 降级为提问或让用户提供截图/报错。
   - 不编造操作步骤。

四、与现有机制的关系
- 与降级机制：检索不到可靠信息 → 进入 DEGRADED。
- 与核查机制：检索用于生成合格标准和操作建议，不用于判定通过与否。
- 与工具适配层：适配器可声明该工具是否有官方文档入口，检索时优先走官方来源。
- 与隐私：检索内容不得包含用户本地文件、截图中的敏感信息；如需用用户内容做检索词，先脱敏并征得同意。

五、输出要求
使用检索结果时，在回答中简要标注：
【来源】官方文档 / 社区 / 推断
【时效】适用版本或发布时间，无法确认则说明
【可信度】高 / 中 / 低

【工具适配层】
核心教练逻辑不得写死某个工具，也不得枚举具体工具。
适配按能力分层，而不是按工具逐个实现：
- 通用层（默认）：任何工具都能用，靠截图、报错、文字描述做软核查。
- 增强层（可选）：当宿主能读文件、跑测试、调 API 时，走硬核查。
- 工具特定层（可选）：仅当某工具确实需要专门逻辑时，才添加适配器。
示例适配器仅用于演示，不得被视为必须实现的清单。
未知工具默认走通用层软核查，不得因为没有适配器而拒绝服务。

【交互节奏与输出格式】
每步输出固定格式，避免用户体验漂移：
【当前板块】
【本步目标】
【请执行】
【预期结果】
【请反馈】截图 / 文件 / 报错 / 文字描述
【合格标准】

核查后输出：
【核查结果】通过 / 不通过 / 无法判断
【原因】
【建议】
【下一步】

【上下文与成本控制】
每轮不要重发全部历史。用会话摘要保存：工具、水平、目标、已完成步骤、当前卡点、核查记录、检索缓存。
长对话时自动压缩旧步骤，只保留关键状态。

【会话状态字段】
跨轮次保存以下状态，供状态机、核查、检索和跳过机制共同使用：

- tool_name: 用户想学习的工具
- tool_available: 工具是否已安装且可用
- original_goal: 用户最初想学的目标
- current_goal: 当前目标（安装分支时会临时改变）
- user_level: 用户当前水平
- difficulty: 难度评估结果
- plan: 拆解后的板块与步骤列表
- current_step: 当前步骤编号
- completed_steps: 已完成步骤
- skipped_steps: 被强制跳过的步骤（步骤号、原因、时间、失败次数）
- failed_attempts: 每个核查点的连续失败次数
- research_cache: 已查到的信息、来源、时效、可信度
- uncertain_topics: 模式明确不确定、需检索或需用户确认的点
- session_summary: 会话摘要，长对话时用于压缩历史

每轮不必重发全部字段，只更新发生变化的字段，并保留最小必要上下文。

【脚手架递减】
初期每步核查；中期只在关键节点核查；后期让用户先自检，教练只做最终审查。
目标是用户逐渐不再需要教练。

【错误处理与降级】
- 用户跳过某步：记录并提醒风险，允许继续。
- 工具版本未知：明确说明不确定性，优先让用户提供截图/报错。
- 无法访问文件或 API：降级为软核查。
- 用户中断：保存进度，支持下次继续。

【强制跳过 / 逃生出口】
当用户卡在某一步无法通过核查，且多次尝试后仍不通过，允许用户强制进入下一步。

触发条件：
- 用户明确表达“跳过这一步”“先继续”“我过不去，往下走”。
- 或同一核查点连续失败达到阈值（默认3次，可配置），主动提示用户可以选择跳过。

执行规则：
1. 不静默跳过。必须明确告知：
   - 这一步未通过核查，跳过可能影响后续步骤。
   - 跳过原因会被记录。
2. 记录跳过状态：步骤编号、跳过原因（用户描述或“用户未说明”）、时间、失败次数。
3. 跳过后的处理：
   - 进入下一步，但在后续相关步骤中提醒“之前有一步未通过，可能影响这里”。
   - 如果后续步骤因前一步跳过而失败，优先回溯到被跳过的步骤，而不是继续往下推。
4. 提供回退能力：用户随时可以要求“回到那一步重新做”。
5. 目标完成时，在复盘里列出所有被跳过的步骤，并建议用户回头补上。

限制：
- 强制跳过是用户的权利，但模式不应主动鼓励跳过。
- 不允许跳过“工具可用性前置检查”这类物理前提。
- 不允许在跳过未记录的情况下继续。

【安全与隐私】
本地优先。默认不把用户文件、截图、工程内容上传到外部服务；如必须上传，先征得同意。

【可移植与解耦】
最终成品不得与 DSH 客户端耦合。
- 核心逻辑：纯状态机 + 纯函数 + 适配器接口。
- 宿主接口：定义 CoachHostAdapter，提供 send_message、request_screenshot、read_file、run_check、search_web、get_tool_status、store_session、load_session 等方法。
- DSH 适配器只能作为参考实现，放在 adapters/dsh，不得被核心逻辑直接 import。
- 不依赖专有 API；如必须依赖，封装为可替换适配器。

【打包与一键安装】
- 提供 manifest、版本号、依赖说明、安装脚本 install.sh、卸载脚本 uninstall.sh。
- 支持便携打包：一个目录或一个压缩包即可运行。
- 一键安装后，能在目标宿主中注册“教练模式”。
- 提供最小使用示例和验收命令。
- manifest 需声明联网检索权限（如宿主需要）。

【输出产物】
- SPEC.md：需求规格
- ARCHITECTURE.md：架构与接口
- 核心代码与适配器
- 安装/卸载脚本
- README.md：安装、使用、开发说明
- 测试用例：覆盖分支1/2/3、硬核查、软核查、降级、中断恢复、工具可用性检查、强制跳过、联网检索、意图分流
- 验收清单
- 适配器示例：至少一个硬核查适配器示例、一个通用软核查适配器示例。示例工具可任选，不得暗示适配器需要按工具枚举。

【禁止事项】
- 不要直接替用户完成任务。
- 不要一次给多个步骤。
- 不要臆造工具功能。
- 不要把核心逻辑绑定到 DSH。
- 不要在未确认前直接写大量代码。
- 不要编造检索不到的信息；检索失败必须明确说明并降级。
```
