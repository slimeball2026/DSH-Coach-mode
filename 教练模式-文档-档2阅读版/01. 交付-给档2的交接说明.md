## 三、已实测的机制事实（不要重新论证）

### 能用的（全部经 `cordis_inspect_query` + 安装副本源码双重确认）

| 能力 | 落法 |
|---|---|
| 每轮动态状态块 | `ctx.systemPrompt.context({ name, order, text: (c) => string })`；`c.agent` 可用（`assembleContextFor` 保证） |
| 提示词段落（静态） | `ctx.systemPrompt.section({ name, order, text })`，`order` 用 `getSectionOrder('PLAN_POLICY')` 这类具名常量 |
| 工具注册 | `ctx.tools.register(原始 ToolDefinition)`；**只校验 `output.schema`**（`assertSupportedJsonSchema`，要求 object 根），**完全不校验 `parameters`** |
| 确定性拒绝 | `ctx.tools.guard((exec) => string \| undefined)`，返回字符串即拒绝；分层解析，无人能强制放行 |
| 只读文件核查 | `ctx.fs.resolve/stat/listDir/readText`；`stat` 不存在返回 `undefined` |
| 只读命令核查 | `ctx.subprocess.spawn({ argv, cwd, stdio:{stdout:{maxBytes}}, graceMs, signal })` |
| 会话日志（同步） | `agent.session.snapshotEvents(from, to)`、`ownEvents()`、`seq`、`append()` |
| 结构化工具事实落盘 | `output.presentationMeta(args,value)` → 写进 `tool/result.data.meta`（agent-loop 明确 append） |
| 会话事件类型 | `tool/call`、`tool/result`、`user/message`（`data.source.kind==='user'` 才是真人）、`assistant/message`、`system/message`、`agent-preset/selected`、`session` 头 |

### 不可用 / 会误导

| 坑 | 事实 |
|---|---|
| profile 装的 bundle **不能 import 宿主包** | dsh 的包在 `app.asar` 内，不在 profile 任何祖先 `node_modules` 里 → `ERR_MODULE_NOT_FOUND` → **整行插件加载失败、preset 显示「加载失败」** |
| **服务可用 ≠ 模块可 import** | `ctx.fs` / `ctx.subprocess` 能调用；`import '@deepseek-ai/dsh-tools'` 不行。这是档 1 最贵的一课 |
| preset 的子插件行**不出现在 Config 目录** | `Config.listConfigs` 查 `@local/coach-mode` 永远空；`@deepseek-ai/dsh-persona` 也空。**判子行是否活着只能靠"会话里真能看到那几个工具"** |
| `session` 头里的 `agentPreset` 不可信 | 那是建会话时的默认值；实际生效看 `agent-preset/selected` 事件 |
| `node --test test/` 在本机不可用 | Node **24.21** 把目录位置参数当单个入口模块 → 报 `ERR_UNSUPPORTED_DIR_IMPORT`；且默认 test isolation 的管道子进程在工作区沙箱下 `EPERM`。用 `--test --test-isolation=none`（自动发现） |
| `install_bundle` 重复装同一目录 | 返回 `application: failed, error.code: "ambiguous-install"` —— **不是错误**，意思是"已装且依赖没变化"。要强制重装得先 `remove_bundle`（或改用 `.tgz` 装，依赖串一变就会被识别为变更） |
| 助手正文的软换行会被吃掉 | DSH 的 markdown 渲染器只在 mdast `break`（硬换行）时插 `<br>`；段内单个换行塌成空格。所以**人设里三处固定格式的字段之间必须空行**，删掉就会挤成一行 |
| **宿主提供的提示词变量会随版本增删** | `{{...}}` 只在宿主注册过时才成立。0.2.0-rc.2 有 `cwd`、0.2.1-rc.1 **只剩 `provider` / `model`**。引用不存在的变量不是降级，是**每一轮请求硬失败**（详坑 7） |

**坑 6 · 教练不爱建计划**：v2.1 时有 5 个会话卡在 `INIT` 再也不调 `coach_plan`，于是所有工具被拒。
现在靠 INIT 状态块的命令式文案 + 人设的"最高优先级提醒"兜住。**如果你加新状态，注意别再造出"只能干聊"的死角。**

**坑 7 · 宿主提示词变量随版本增删（0.2.1 的真实事故）**

现象：升级客户端后模式能选中，但**发任何一条消息都失败**：

```
本轮运行失败 unknown prompt variable "{{cwd}}" in section "deployment:persona-suffix";
registered variables: provider, model
```

根因：档 0 的 persona 里写着 `suffix: Your working directory is {{cwd}}.`，
而 `cwd` 是**宿主注册的提示词变量**——0.2.0-rc.2 有，0.2.1-rc.1 **没有了**。
一个不存在的变量 → 渲染那一段直接抛错 → **不是降级，是每一轮请求都失败**。

修法（v0.2.4）：**删掉整条 suffix**（persona 的 `suffix` 默认 `''`，仍会遮蔽部署级 suffix，只是渲染为空）；
工作目录改由插件状态块的【位置关系】行给出，不再依赖提示词变量。

自查方式：官方 preset 是人设写法的唯一权威——`dsh-web-app/presets/*.patch.yml` 里
**只有 `{{model}}`**，全仓没有 `{{cwd}}`。要确认当前版本注册了哪些变量，看报错里那句
"registered variables: …"，或读 `dsh-system-prompt` 的 `variable()` 调用点。

**顺带的 BOM 坑**：改 `package.json` **不要**用 PowerShell 的 `Set-Content -Encoding utf8`
（会加 BOM，`JSON.parse` 抛 `Unexpected token '﻿'`，Loader 读 manifest 也会炸）。

## 六、状态机与数据模型的现状

**8 个阶段**（4 个驻留 + 2 个过渡，另有 2 个特殊）：

```
INIT ──coach_plan(可用性未知)──▶ CHECK_TOOL_AVAILABILITY ──coach_plan(补齐)──▶ PLAN
INIT ──coach_plan(可用性已知)──────────────────────────────────────────────▶ PLAN
PLAN ──受理──▶ WAIT_FEEDBACK ──coach_check/coach_verify──▶ VERIFY_DONE
VERIFY_DONE ──通过──▶ NEXT_STEP ──coach_advance──▶ WAIT_FEEDBACK / COMPLETE / PLAN(安装收尾)
VERIFY_DONE ──不通过──▶ WAIT_FEEDBACK（失败 +1）
VERIFY_DONE ──无法判断且无证据──▶ DEGRADED
WAIT_FEEDBACK / VERIFY_DONE / DEGRADED ──coach_skip──▶ NEXT_STEP
```

- 过渡态：`PLAN`、`NEXT_STEP`（同一次工具调用内进出）。
- `INIT` / `CHECK_TOOL_AVAILABILITY` 阶段允许 `coach_check`，记为**环境核查**（`stepKey="env"`），**不推进阶段**。
- 其余工具在这两个阶段一律拒绝。

**CoachState**（`core/machine.js` 的 `initialState()`）：
`stateVersion=1`、`phase`、`toolName`、`toolAvailable`、`userLevel`、`originalGoal`、`currentGoal`、`goalMode`、
`difficulty`、`plan[{section, steps[{goal,action,expected,standard,evidence,check,skipped,skipReason,failedAttempts}]}]`、
`sectionIndex`、`stepIndex`、`checks[{stepKey,kind,target,ok,detail,at}]`、
`verifications[{stepKey,verdict,evidenceRef,reason,at}]`、`skips[{stepKey,reason,at,failedAttempts}]`、
`planAcceptedAt`、`pendingNoInfoAt`。

**折叠语义（改字段一定要把 `stateVersion` 加一）**：

- 只吃**成功**的工具结果（`data.error` 为空且 `message.isError !== true`），失败调用不推进状态；
- `checks[].ok/detail` 来自 `tool/result.data.meta`；
- **也折叠真人用户消息**：短且属"零信息"说法（不行 / 还是不行 / 没反应…）计入 `failedAttempts`，
  **一轮只计一次**（随后 `coach_verify` 失败只认领 `pendingNoInfoAt`，不重复加）；
- `at` 一律取事件 `seq`。

**工具前置条件（`core/verify.js`，这是本切片的命根子，别放松）**：

1. `evidence ∈ {file,command}` 且本步无 `coach_check` → `coach_verify` 直接失败；
2. `evidence === 'none'` 只允许判「无法判断」；
3. `evidence === 'user_artifact'` 判「通过」必须给 `evidenceRef`；
4. `coach_advance` 要求上一步已有「通过」或「跳过」记录；
5. 同一步重复核查必须引用**新的** `coach_check` 证据（新证据 seq > 上一条结论 seq）。

## 九、给档 2 的入场建议

1. **先跑一遍现有单测和冒烟**，确认基线是绿的，再动手。
2. **加状态之前先想清楚"模型为什么会走到它"**。档 1 最大的教训是：状态机把路堵死，模型就会卡在 `INIT` 干聊。
   每加一个阶段，都要问：进入它的工具入口是什么？出口有几个？如果模型不配合，它会不会变成死角？
3. **不要为了"更强制"去放松第 6 节那五条前置条件**——它们是本切片唯一真正"物理"的东西。
4. **改 `core/` 之前先写测试**。纯核心零依赖，`--test-isolation=none` 迭代很快。
5. **改完必须"覆盖安装 + 重启"两件都做**：只重启不重装，失败的 preset 声明会带着诊断挂在名单上；
   只重装不重启，跑的是旧模块代。改的是 `link:` 所以覆盖安装通常只需重启——但声明行改了就必须重装。
6. **验收一律以日志为准**，用 `coach-recheck.cjs` 出证据（会话 id + 事件 seq），不接受"应该可以"。
