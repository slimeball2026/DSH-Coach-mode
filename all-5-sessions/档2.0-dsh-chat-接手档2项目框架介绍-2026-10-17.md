##### 一、框架

一句话：**档 0 = 纯提示词 preset；档 1 = 在它上面加“插件持有状态 + 5 个工具 + 每轮状态块 + write/edit 守卫”；档 2 = 剩下的全部。**

运行形态：

```
bundle ([package.json](coach-mode-bundle/package.json) + [cordis.patch.yml](coach-mode-bundle/cordis.patch.yml))
  └─ insert preset-coach (agent preset, id=coach)
       plugins:
         persona        ← 人设/固定格式/意图分流/跳过规则（静态前缀）
         coach-engine   ← [index.js](coach-mode-bundle/index.js)：状态块 + guard + 5 个工具
         tool-ask-user / tool-fs / tool-fs-search / tool-web / tool-pwsh / tool-bash
         compaction     ← group: compaction-basic + command-compact + tool-result-pruner
```

只有选「教练模式」的会话才有这 9 行；标准模式看不到。

机制上最关键的一点：**插件不存状态，状态从会话日志折叠出来。**

```
session log (tool/call, tool/result.data.meta, user/message)
   │ foldItems() 纯函数，按 seq
   ▼
CoachState ──render──▶ 每轮状态块（systemPrompt.context, order 130）
   ▲
   │ 工具 execute 先 stateForExec() 折出当前状态做校验；
   │ 成功后只返回 value + presentationMeta → 宿主写进 tool/result.data.meta
```

所以真源是日志；工具只“申请”转移，插件校验；不新增事件类型、不用 storage、不注册投影（D3/D4）。状态块是“本快照取代上一份”，每轮都在、不累积。当前 8 个状态、5 个工具、四条 `coach_verify` 前置 + 一条“新证据”规则；`PLAN` / `NEXT_STEP` 是过渡态。

三层边界：`core/` 纯函数、零宿主 import；适配层才碰 `ctx.*`；整包禁止 `import '@deepseek-ai/*'`——因为宿主包在 `app.asar` 里，profile 的 bundle 解析不到，一旦 import 就是整行加载失败。这条是档 1 最贵的教训。档 1 的验收基线是 A1–A7；A7 的 12 条权威副本在 [05. 00-交接说明.md](<教练模式-文档-档2阅读版/05. 00-交接说明.md>) §9，不在 README。

##### 四、我读日志发现的两个现成缺陷

这两条不是“档 2 功能”，是 0.2.4 现在就有的，建议先修：

**1. 空 `sections` 的 `coach_plan` 会把模型锁在“确认环境”。**
[core/plan.js](coach-mode-bundle/core/plan.js:206) 里只要 `payload.plan.length === 0` 就无条件进 `CHECK_TOOL_AVAILABILITY`，不看 `toolAvailable`；[tools/coach-plan.js](coach-mode-bundle/tools/coach-plan.js:115) 的返回文案又固定说“工具可用性还是未知”，即使模型传的是 `yes`。加上状态块让“还没拆出步骤就把 sections 留空，只报可用性”，两边一起把模型推回循环。
实机证据：`77495b5d` 从 seq 26 到 74 连续 8 次 `coach_plan`（`toolAvailable:"yes"`），每次返回“还是未知”，会话一直停在「确认环境」，用户始终没拿到第一步。
修法：空 sections 且可用性已知时不要进 CHECK，返回“可用性已记录，请提交 steps”；返回文案按 availability 判断，不要按 phase 判断。

**2. `coach_check` 的 `kind` 没有在 execute 里校验。**
[tools/coach-check.js](coach-mode-bundle/tools/coach-check.js:167) 只分 `command` 和“其他”，“其他”一律走文件路径。宿主不校验 `parameters`（R10），所以实机 `6899f1df` 的 seq 64→65 出现了 `coach_check({kind:"none", target:"none"})`，被当成文件路径记录成环境核查。修法：execute 开头对 `CHECK_KINDS` 做白名单校验。

另外一条是产品缺口，不是代码 bug：模型会跳过“问水平”——`77495b5d` 用户直接抱怨“你怎么都没问我的水平如何”。`userLevel` 在 `coach_plan` 里是可选的，状态机不强制。要不要把“问水平/问目标”变成 plan 的硬前置，属于 Q2 的一部分，你定。

##### Q1 · 先做哪一块

**白话**：档 2 不是“一件事”，是六件事捆在一起：修现有缺陷、做四个新关卡、做检索、做暂停/恢复、做界面、做收尾。先动哪个？

- **A. 先修 bug，再做检索（我的建议）**：先用 1–2 天把 0.2.4 的“确认环境”死循环和 `kind` 校验补掉，再动 `RESEARCH` + 检索。你短期看不到新功能，但后面每步都站在稳的基线上，返工最少。

##### Q2 · 四个新关卡怎么“落地”

**白话**：现在插件有 8 个关卡，规格要 12 个。新增四个是：`INSTALL_TOOL`（把“安装工具”当成临时关卡）、`RESEARCH`（要查资料时的关卡）、`CLARIFY_ERROR`（用户说不清时的关卡）、`DIAGNOSE_ERROR`（用户说清楚了、教练要诊断时的关卡）。问题是：这四个要做成**真关卡**，还是只在提示词里写“遇到这种情况按这个流程走”？

**关键约束**：关卡必须有“门”和“出口”。没有工具能把状态推进去，模型永远到不了这个关卡；没有工具能出来，就会卡死。档 1 的 `INIT` 卡死过 5 个会话，就是这个原因。

**几条路意味着什么**：

- **A. 每个新关卡配一个工具（真关卡）**：模型必须按按钮才能进/出。可控、可验收；代价是工具从 5 个变多，模型可能不按按钮，代码和测试量增加。
- **B. 插件自动判断**：看用户这句话是“不行”还是“报错：xxx”，自动切关卡。不加工具；代价是靠关键词/长度分类，容易误判，误判后用户被卡在错误关卡。
- **C. 混合（我的建议）**：只给“模型必须做决定”的加工具（比如 `coach_research`、`coach_back`）；`CLARIFY_ERROR` / `DIAGNOSE_ERROR` 先留在“等待反馈”里当分支，等行为稳定再升级成真关卡。不追求“12 个都成为关卡”，而是该硬的硬、该软的软。

##### Q3 · 查资料的“小本本”放哪

**白话**：`research_cache` 就是教练的查资料小本本：查了什么、来源是哪、适用版本/日期、可信度高不高。有了它，教练不用重复查，也能在回答里标来源。问题是这本小本本放在哪里。

**为什么难**：现在的规矩是“一切状态都能从聊天记录重算”，但 `web_search` 是宿主工具，它的结果不会自动进教练的结构化记录。

**几条路意味着什么**：

- **a. 新增 `coach_research` 工具**：教练查资料必须走这个按钮，按钮把来源/时效/可信度写成结构化便签。好处是能回放、能验收、不破坏“日志是唯一真源”；代价是模型可能偷懒直接用 `web_search` 绕过它。宿主确实有 `ctx.web` 服务，所以技术上可行；要不要把 `web_search` 收起来、只留 `coach_research`，是另一个小决定。
- **b. 在门口拦截 `web_search` / `web_fetch`**：不管模型用哪个搜索，都在拦截器里自动记录、自动脱敏。好处是防绕过；代价是要确认宿主 API 允不允许在拦截器里写结构化信息，技术上最不确定。
- **c. 用 `ctx.storage` 另开一个存储**：最简单，还能跨会话；代价是违反“日志是唯一真源”，回放/fork 可能对不上，多一个要维护的东西。

**脱敏**（搜索词里不能带你的本地路径、截图敏感信息）也走同一条通道：a 在工具参数里脱敏，b 在拦截器里改参数，c 在存之前脱敏。

##### Q4 · 暂停、恢复、回退

**白话**：这是三件不同的事：

- **同会话恢复**：关掉 DSH 再打开同一个会话，状态能靠聊天记录算回来——**这个现在已经支持**。
- **跨会话续接**：下次开一个**新会话**，教练不知道你之前学到哪——现在不支持。
- **回退**：你说“回到第 2 步”，教练得往回走。聊天记录是账本，只能追加“回到第 2 步”这条记录，不能擦掉旧记录。
